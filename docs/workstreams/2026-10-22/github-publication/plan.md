# Подготовка Music Critic V2 к публикации на GitHub

Дата проверки: 22 октября 2026 года. Это план, а не выполненная реорганизация.
Код, конфиги, история Git, существующие ветки и записи экспериментов не менялись.
Коммиты, push и PR в этой задаче не выполнялись.

## Рекомендация

Продолжать существующий `nairary/music_critic_v2` как исследовательский
репозиторий. Сделать понятный вход для читателя и отдельный маршрут
воспроизведения экспериментов. Сначала улучшить навигацию и упаковку;
не удалять экспериментальный код и не переписывать историю ради небольшого
числа конфигов. Данные и полные результаты остаются вне Git.

`src/music_critic/experiments/` нельзя просто исключить как одноразовые
опыты: текущий `critic/c3_backbone.py` импортирует из него граф и модель
temporal C3, а C4 использует те же контракты, граф и транспозиции.
Перенос этих модулей требует отдельной миграции импортов и проверки
совместимости с сохранёнными состояниями. Для первого выпуска это не нужно.

также не предназначены для обычной Git-истории.

## Какие подсистемы входят в проект

1. Каноническое представление музыки: точное время, ноты, дорожки,
   сериализация, маски и валидация; адаптеры MIDI, HookTheory, POP909-CL,
   Dilemmadata, PDMX и TAVERN.
2. Графы и классификаторы C0–C4: локальные и иерархические представления,
   временные события, 18 музыкально-теоретических выходов и варианты обмена
   информацией между задачами.
3. SSL: маскирование и восстановление представлений нескольких уровней.
4. Парный критик: frozen C3, головы аспектов, данные правок и обучение
   сравнению вариантов.
5. HCM в `pll/`: условное восстановление событий, локальный и полный
   контекст произведения, многоуровневая память и мотивы.
6. Подготовка разметки: объединение источников, связи нот, гармонические
   контексты, разборы, проверки полноты и численный экспорт.
7. Инфраструктура исследований: обучение/возобновление, CPU/GPU и cloud
   сценарии, реестр, проверки артефактов, восстановление внешних данных и CI.

Наличие подсистемы в коде не означает готовый пользовательский сервис или
проверенное качество каждого режима. В публичной документации отдельно
отмечать реализацию, проверенный запуск и научный результат.

## Что действительно создаёт путаницу

- README одновременно описывает старые фазы и утверждает, что preference
  training/PLL ещё не реализованы; локально уже есть `critic/`, `pll/`
  и соответствующие записи запусков. `configs/README.md` всё ещё описывает
  bootstrap Phase 0. Эти страницы нужно обновить раньше перестановки файлов.
- Из 151 сценария пользователь не понимает, какие нужны для первого запуска,
  а какие принадлежат исторической проверке или облачному оператору.
- Часть настроек задаётся через Hydra ConfigStore и Python dataclasses,
  часть — JSON, реальные конфиги конкретных запусков часто находятся
  в игнорируемых артефактах. Удаление `configs/` не упрощает эту поверхность.
- `configs/pll/hcm1_reference.json` и `hcm1_whole_reference.json` явно
  помечены как reference templates / not-admitted. Их нельзя представить
  как точные конфиги обученных состояний статьи.
- `STATUS.md` вырос примерно до 1,06 МБ. Это полезный журнал, но неудобная
  стартовая страница. Нужна короткая текущая сводка перед подробной историей.
- В корне нет `LICENSE` и `CITATION.cff`. Лицензия адаптированных агентских
  skills уже сохранена отдельно; она не является лицензией всего проекта.
- `.omo/` содержит три локальных session-continuation файла и пока не
  исключён. `.env.local` также не покрывается текущим правилом `.env`.
  Ни то ни другое не нужно в публичной поставке.
- В 132 документах есть машинные абсолютные пути. Часть — честная provenance
  старых запусков, часть мешает повторению команд на другой машине. Сначала
  исправлять примеры и добавить переносимые ссылки; не изменять терминальные
  записи и их хеши ради косметического удаления путей.

## Что оставить в Git

| Категория | Решение |
|---|---|
| Пакет, связанные тесты и маленькие синтетические фикстуры | Публиковать вместе; не обрезать тесты ради внешнего вида |
| C0/C1/C2 и отвергнутые варианты | Сохранить как исследовательские контроли; показать статус в индексе |
| Нужные сценарии запуска | Сохранить; дать 6 понятных маршрутов, остальные связать с протоколами |
| Исторические конфиги и attestations | Сохранить существующие пути на первом этапе; отдельно отметить назначение |
| Реестр и ledger | Сохранить все 306 записей, включая отрицательные результаты; добавить читабельную сводку |
| Контракты и история решений | Сохранить; короткую навигацию поставить перед журналами |
| `.agents/` и `AGENTS.md` | Можно оставить как инструменты разработки с уже включённой атрибуцией |
| Статья, рисунки, LaTeX | Выбрать публикуемую редакцию отдельно; не заливать все рабочие PDF и черновики автоматически |

Статусы реестра на дату проверки:239 completed, 33 failed, 20 aborted,

## Что хранить отдельно

Датасеты, MIDI/audio корпуса, checkpoints, target/cache shards, веса,
полные журналы, source/data evidence archives, окружения и локальные
сессии. Использовать существующее внешнее хранилище; в Git оставлять
идентификатор версии, SHA-256, размер, условия доступа и инструкции получения.
Лицензии данных и моделей учитывать отдельно от лицензии кода. Не публиковать
ключи для доступа к частному хранилищу и не обещать публичную загрузку того,
что пока доступно только локально/в частном бакете.

## Предлагаемая витрина, без массового переноса исходников

```text
README.md                    цель, текущие возможности, быстрый старт
LICENSE                      выбранная лицензия проекта
CITATION.cff                 как ссылаться на код/публикацию
pyproject.toml               установка и явные дополнительные окружения
src/music_critic/            текущий пакет, пути сохраняются
tests/                       тесты и синтетические фикстуры
configs/README.md            карта: пример / шаблон / исторический конфиг
configs/...                  существующие пути сохраняются
examples/                    небольшой пример без внешнего корпуса и весов
docs/GETTING_STARTED.md       проверенный маршрут первого запуска
docs/MODELS.md                C0–C4, critic, HCM-1/HCM-2 и их ограничения
docs/REPRODUCIBILITY.md       модель → опыт → конфиг → данные → checkpoint
docs/experiments/README.md    результаты, контроли и неудачные гипотезы
docs/experiments/records/     неизменяемая машинная история
docs/...                     подробные контракты и исследования
```

Новые имена выше — предложение, а не уже созданные файлы. Первая версия
не требует превращать все старые сценарии в один общий CLI или переносить
весь `src/experiments` в новый пакет. Это отдельный рефакторинг с тестами,
если навигация и рецепты не решат проблему.

## Как упорядочить конфиги

В `configs/README.md` перечислить 15 JSON по назначению и владельцу CLI:
данные/пример (`pdmx`), локальный контроль, историческая реконструкция
`phase9eb1`, SSL и два шаблона HCM. Исторические attestation/environment/
reported-metrics файлы не выдавать за варианты настройки современной модели.

Затем добавить шесть проверенных рецептов:

1. Маленький CPU-пример построения/чтения музыкального графа.
2. Теоретический классификатор: выбранная C3, с явными вариантами C0/C1/C2/C4.
3. Парный критик: входные пары, checkpoint и формат оценки.
4. HCM-1: локальное условное восстановление/оценка.
5. HCM-2: полный контекст и соответствующие ограничения памяти.
6. Подготовка и экспорт теоретической разметки.

Для каждого рецепта: готовность, точная команда, нужный конфиг, зависимости,
источник данных/весов, ожидаемый файл результата и границы проверки. Пример
конфига с переносимыми путями и исторический замороженный конфиг — разные
артефакты; между ними нужна явная ссылка, а не тихая правка старого файла.
Не добавлять ещё одну конфигурационную систему поверх существующих.

Для старого AnalysisGNN common benchmark отдельно задокументировать pinned
GraphMuse environment: он используется двумя модулями и сейчас не объявлен
в корневом `pyproject.toml`. Hydra/OmegaConf и NumPy также требуют явного
описания окружений/прямых зависимостей по поддерживаемым маршрутам, а не
расчёта на случайно наполненный локальный venv. Это не решение устанавливать
все зависимости всех исторических опытов в одно окружение.

## Последовательность подготовки релиза

1. Зафиксировать состав текущих tracked+untracked исходников отдельным
   проверяемым source snapshot. Git bundle сохраняет коммиты/refs, но не
   заменяет резервную копию 602 неотслеживаемых файлов и рабочего diff.
2. Подготовить ветку выпуска на основе текущей истории, сохранив связанные
   код, тесты и протоколы как целый проверенный снимок. Новый worktree сам
   по себе не переносит нынешние незакоммиченные файлы.
3. Обновить `.gitignore` для `.omo/` и `.env.*`, оставив `.env.example`.
   Проверить окончательный allowlist публикации и историю на credentials;
   не применять слепое `git add .`.
4. Обновить README, карту моделей и карту конфигов. Сохранить подробную
   историю за ссылками; не удалять доказательства и не менять терминальные
   experiment records.
5. Подготовить лицензию, атрибуцию сторонних компонентов и citation metadata.
   Лицензию не выбирать автоматически по наличию MIT у одного из skills.
6. Проверить установку и публичные команды в чистой копии, где нет
   `outputs/`, `data/`, частных путей и заполненного venv. Базовый CPU-пример
   должен работать на синтетических фикстурах. Полный CI и нужные
   воспроизводимые маршруты проверить на точном финальном составе файлов.
7. Отдельно проверить конфиги/ссылки для результатов статьи: все ли нужные
   веса/данные доступны получателю. Не обещать полное воспроизведение только
   на основании hash-записи в реестре.
8. Публиковать reviewable-коммитами через PR в существующий репозиторий,
   проверить CI и отметить источник релизным тегом. Не делать force-push,
   orphan-историю, массовое удаление веток или публикацию всех веток.

README должен занимать несколько понятных экранов: задача → схема моделей →
первый запуск → основные результаты и ограничения → ссылки на детали.
Для clone важна эта навигация, а не отсутствие исследовательской истории.
