## Общий научный контроль

- TEST закрыт: не создавать его loader, не читать inputs/targets и не вычислять метрики.
- C0/C2 и их исходные checkpoints, 18-head ontology, split, historical transposition и terminal records неизменны. Новое поведение — отдельный opt-in эксперимент.
- C2 — seed-17 кандидат, не доказанный универсальный победитель. Историческая транспозиция оставляла track pitch summaries прежними; WS1 feature-complete profile является другим изменением.
- Готовность кода, CPU smoke, CUDA gate и качество на реальных данных — разные результаты.
- POP уже использован для внешней диагностики. Настройка по его labels — development/adaptation, не новое независимое zero-shot доказательство. Использовать Dilemma VALIDATION для заранее заданного выбора. Не менять frozen POP projection и не исключать неудачные классы.
- Missing/unknown labels маскируются. Gold chord/voice/phrase boundaries и theory labels не входят в обязательные inputs. Raw unlabeled MIDI inference сохраняется.
- Деградации на этой стадии используются для оценки. Не добавлять preference/contrastive critic training; latent reconstruction error не называть PLL или качеством музыки.
- Каждый существенный run/import/decision-changing diagnostic регистрировать до запуска по EXPERIMENT_LOGGING; immutable failures сохранять, ledger генерировать инструментом. Полные артефакты только в ignored outputs собственного worktree.
- Модели не объединять между задачами до отдельных сравнений. У каждой абляции свой контроль из одной проверенной исходной C2, одинаковые данные и заранее заданный бюджет; добавочную стоимость учитывать отдельно.

## Работа и очередь GPU

Локальная разработка, маленькие synthetic tests, разбор уже сохранённых разрешённых артефактов могут идти параллельно. CPU-thread count и объём файлов ограничивать, не строить глобальные corpus caches.
Новые SSH-подключения, GPU, дорогое real-data training/evaluation и крупные preprocessing jobs в дочерних задачах не запускать самостоятельно: передать координатору конкретный запуск с ID, командой, ресурсами и проверками. Это распределение ресурса между тремя задачами, а не просьба снова получить разрешение пользователя. Координатор выполняет уже разрешённую работу и выдаёт одно место в GPU-очереди после review; текущая занятость сервера не предполагается известной.

В собственном worktree обновить STATUS. Терминальные experiment records не менять; новые ID имеют префикс своей задачи. Не коммитить, не пушить и не сливать ветки на этом шаге. Legacy не нужен и остаётся read-only.
Готовые результаты один раз отправить координатору через send_message_to_thread: название задачи, абсолютный worktree, исходный snapshot hash, собственные изменённые файлы, тесты, артефакты/ID, конкретные блокеры и следующий исполнимый шаг. Самостоятельные циклы опроса и дополнительные задачи/автоматизации не создавать.

## Критерий завершения первого этапа

Исполнимый ограниченный инструмент или конфигурация, тесты необходимых механизмов, документированный научный протокол, честные границы и пакет для независимого review. Если исходных данных или checkpoint bindings нет, завершить независимую реализацию, точно перечислить недостающее и передать координатору; не придумывать bindings и не останавливаться на общих рекомендациях.
