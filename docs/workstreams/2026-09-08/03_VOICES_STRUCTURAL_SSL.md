# Задача 3 — Голосовые связи и структурное SSL

Цель первого этапа: подготовить один изолированный пилот группового маскирования на существующей C2→SSL базе и отдельно проверить реализуемость голосовой задачи. Это две гипотезы, не одновременное изменение encoder и objective.

Прочитать docs/WS2_THEORY_SSL_HARNESS.md, docs/PHASE8A_HIERARCHICAL_MASKING.md, Phase 7/8 документы по фактическим imports, docs/PDMX_PIPELINE_CONTRACT.md, docs/HARMONIC_MODIFIERS_FUTURE.md и обзор в read-only основном checkout outputs/research/music-understanding-20260908/report-source.md.
Исследовать существующие ssl/model.py, objective.py, multilevel.py, theory_warmstart.py и theory_retention_harness.py. Уже есть detached full-view latent targets; shared target encoder без EMA. Не выдавать это за отсутствующий JEPA и не переписывать механизм только ради нового названия.

1. Выбрать из существующих masking policies минимальное сравнение random note masking против скрытой музыкальной группы (доля или такт). Сначала проверить, не реализовано ли оно уже; переиспользовать. Новая группа должна иметь raw-derived boundaries, а не gold chord/phrase spans. Не добавлять в первый pilot EMA teacher, voice edges, новый encoder или новый latent loss.
2. Сделать отдельный bounded runner/config adapter, строго связывающий проверенное C2 model-only состояние с existing WS2 shared backbone и сохранёнными 18 theory heads. Явно перечислить transferred/retained/fresh/inactive weights и optimizer ownership. WS2 сейчас fixture/in-memory harness: не притворяться, что real checkpoint loader, data factory и resume уже готовы.
3. В сравниваемых ветках одинаковые стартовые веса и corpus schedule; заранее учитывать mask density, число скрытых notes/groups и encoder forwards. Theory replay одинаков в обеих ветках; восстановление theoretical skill сравнивать с исходной C2 и соответствующим контролем. Метрики: восстановление, variance/collapse, качество theory tasks, позже context diagnostics. SSL loss сам по себе не критерий музыкального прогресса.
4. CPU-тесты закрывают утечки через pitch class/octave/track summaries и иные зависимые masked features, границы произведений, stop-gradient targets, deterministic masks, shared-parameter updates без дублей optimizer, theory-only/SSL-only paths и interrupted resume. Связать проверки с реально используемыми masking policies; не заявлять feature-complete mask без аудита.
5. Отдельный конкретный voice deliverable: контракт target «следующая нота того же голоса», источник доступных voice annotations и masks/confidence, raw-only candidate edges, маленькие polyphonic fixtures с пересечением голосов и несколькими голосами в дорожке. Не считать track_id gold voice_id и не создавать псевдо-gold из эвристики. Подготовить CPU-tested candidate/target mapping, если существующая схема позволяет изолированную реализацию; иначе точный compatibility report и тесты ограничений. Голосовые edges/heads не включать в первый SSL pilot.
6. PDMX: проверить существующую production-readiness по manifests/контрактам и перечислить недостающие release/license/dedup/split bindings. Не скачивать весь корпус, не создавать глобальный cache, не утверждать readiness по synthetic fixtures. Первый реальный pilot планировать только на проверенном TRAIN corpus с фиксированным ограниченным ресурсным бюджетом; отсутствие данных не мешает закончить mechanics.

Готовность: CPU-tested pilot mechanics/configs, небольшой voice контракт/fixtures, проверка отсутствия дублирования имеющегося SSL, конкретный GPU пакет после review координатора. ID префикс EXP-SSL-GROUP-*; отдельные voice evidence EXP-VOICE-*. Не запускать PDMX-scale training, fusion, modifier heads, PLL/preference/degradation training или TEST.
