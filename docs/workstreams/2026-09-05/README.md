## Научный контекст, обязательный для всех
1. V2 учит представления символической музыки и вспомогательные музыкальные
   задачи для будущего критика. Theory macro-F1 не измеряет эстетическое качество.
2. Текущие corrected C0/C2 имеют 18 активных голов, 8 основных и 10
   вспомогательных. C0-120k ожидает первичных итоговых свидетельств. Не считать
   пользу транспозиции доказанной, не менять активный запуск и frozen profiles.
3. Raw MIDI inference обязателен. Разметка, masks, confidence, split и семантическая
   provenance не являются входами encoder, topology или частью raw graph identity.
   Missing labels маскируются, exact timing сохраняется, gold segmentation не нужна.
4. Используем существующие Phase 7–8 GraphMAE2-inspired latent reconstruction и
   hierarchical masking. Это не буквальная репродукция GraphMAE/GraphMAE2, не
   PLL и не готовая функция качества.
5. Деградации на первом исследовательском этапе предназначены для оценки будущих
   сигналов PLL/fragility. Эта волна не реализует обучение ranking на деградациях,
   вероятностный decoder, learned task weighting или AnalysisGNN reproduction.
6. Для PDMX число 1000 — исторический пример последующей инженерной приемки,
   не лимит корпуса и не обязательная политика выборки.
7. В POP909-CL channel 0 уже содержит melody и accompaniment; channel 1 — только
   аккордовая аннотация. Нельзя добавлять из нее ноты во вход evaluator.
8. Входные словари выводятся из действующего registry. В corrected root 37
   spelled classes, quality 17; не переносить размеры из public AnalysisGNN.

## Правила разработки
- Прочитать AGENTS.md и относящиеся к задаче разделы восьми обязательных документов:
  IMPLEMENTATION_PLAN, ARCHITECTURE, DATA_CONTRACT, EXPERIMENT_LOGGING, ROADMAP,
  STATUS, LEGACY_REFERENCE, DECISIONS; затем профильные контракты и исполняемый код.
  При противоречиях: code/tests → versioned configs/manifests → проверенные records
  → phase docs/ADRs → общие документы → старые prompts.
- До изменения кода назвать фазу, файлы, проверки, legacy scope и non-goals.
  Старый repository read-only, без runtime imports; его доступ не требуется.
- Работать только в собственном worktree. Владение файлами задано в каждом ТЗ.
  Изменение общих graph/schema/vocabulary/trainer APIs за пределами владения
  сначала описать координатору: проблема, минимальный diff, затронутые потребители.
  Не блокировать независимую работу, если можно продолжить в своих файлах.
- Не добавлять зависимости и не менять pyproject.toml. Доступен Python
  `/private/tmp/music-critic-v2-integration-venv/bin/python`
  с pytest, torch, torch_geometric, mido и hydra; проверен координатором.
  Использовать его только как runtime, не модифицировать общее окружение.
  В каждой команде явно выставлять `PYTHONPATH=src` из собственного worktree,
  чтобы editable install не импортировал исходники другой задачи.
- Тесты выполняются на CPU; ограничить OMP/MKL threads, не запускать четыре
  полные suite одновременно. Новые тесты плюс относящиеся регрессии обязательны.
  Fixtures должны быть маленькими и синтетическими; не открывать opt-in real-data
  integration tests. Temporary checkpoints разрешены только созданные тестом.
- В каждом worktree обновить docs/STATUS.md отдельной WS-записью. Новый
  архитектурный контракт при необходимости фиксировать append-only ADR с
  уникальным именем WS1/WS2/WS3/WS4, без переписывания старых ADR. Координатор
  сведет общие документы при интеграции.
- Не переписывать terminal experiment records, ledger и frozen C0/C2 fingerprints.
  Код подготовки будущего запуска разрешен; реальные эксперименты требуют
  отдельного согласованного протокола и planned record до исполнения.
- Не запускать training/evaluation на реальных данных, не открывать TEST
  inputs/targets/loaders, не загружать настоящие обученные checkpoints, не
  использовать SSH и не изменять текущий C0. Synthetic unit-test updates разрешены.
- Не скачивать корпус и не обходить ограничения окружения. Разрешено читать
  публичные первичные определения формата/исходники для contract verification.
- Оставить reviewable diff и точные команды проверок. Не делать push, PR, merge
  в main, git cleanup или изменения чужих worktrees. Локальный commit не нужен
  для первого review; если он уже сделан, указать SHA и base.

## Этапы и критерии приемки
1. Исполнитель сверяет APIs и сообщает краткий implementation plan, затем
   реализует согласованный scope без дополнительного ожидания подтверждения.
2. Первый handoff включает путь worktree, base/HEAD, список изменений, точные
   команды и результаты тестов, ограничения и собственный WS_RESULT.md.
3. Координатор проверяет actual diff и raw-input/target boundaries, сохранение
   frozen protocols, semantics, versioning, errors, tests и соответствие ТЗ.
   Успешного текста исполнителя недостаточно для статуса accepted.
4. При замечаниях координатор отправляет их в ту же задачу с конкретной
   воспроизводимой проверкой. Следующий review относится к новой ревизии
   (HEAD плюс fingerprint diff при незакоммиченных изменениях).
5. После принятия отдельных задач координатор готовит совместную интеграцию
   в изолированной копии и проверяет совместимость. Accepted по одной задаче
   не означает integrated. Публикация и merge в main не входят в эту волну.

Во время этой волны проверка выполнялась каждые 10 минут через thread heartbeat;
после общей приемки heartbeat остановлен. При активной работе можно ждать
завершения одной из задач через wait_threads. Сохранять cursors,
рассмотренные ревизии, замечания и статусы в COORDINATION.json. Не посылать
повторные замечания на ту же ревизию и не прерывать занятого исполнителя только
ради проверки статуса. При неизменном состоянии — тишина. Если одна и та же
причина не решается после трех содержательных циклов, сообщить пользователю
конкретный blocker и продолжить независимые задачи. Остановить heartbeat, когда
все четыре результата приняты и совместная проверка завершена, либо когда
дальнейшая работа целиком требует ответа пользователя. Не создавать новые
задачи/обучения автоматически. Существующие tasks не архивировать.

## Воспроизводимая приемка
Обязательны реальные результаты запуска новых и профильных регрессионных тестов.
Skipped из-за отсутствующих зависимостей не считается passed. Результат
fixture-only подтверждает механику, не corpus readiness или улучшение модели.
Не писать самостоятельные experiment records для обычных unit/contract tests.
Все substantive real-data действия остаются отдельной будущей волной.

## Где хранится состояние
[COORDINATION.json](COORDINATION.json) содержит IDs четырех задач, worktree paths,
base/review identities, cursors, статусы и ссылку на heartbeat. ID — средство
координации; при описании задачи пользователю использовать актуальный title из
приложения. ТЗ и состояние не заменяют scientific experiment registry.
