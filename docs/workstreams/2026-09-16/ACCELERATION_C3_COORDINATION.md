## Задача A — общий FP32-тренер и измерение ускорения

Новая задача проекта в отдельном worktree. Владеет общим prepared/runtime
путём, профилированием и no-attention benchmark. Основные кандидаты:
`temporal_slices/campaign.py`, новый модуль подготовленного пакета, необходимые
точечные расширения encoder/loss и новые тесты. Модуль `c3_attention/` не менять.

1. Сверить main с облачным177e514, учесть bounded endpoint15k, не менять
   архитектуру, batch2, FP32, loss/редукции, sampler/shift/LR, masks и RNG.
2. Разделить измерения queue wait, decode/validate, H2D, forward, alignment/loss,
   backward/optimizer, checkpoint/validation; отдельно обычный полный таймер.
   Инструментирование не должно синхронизировать каждый участок в benchmark.
3. Реализовать минимальный проверяемый пакет оптимизаций: статическая структура
   и ownership на CPU, отдельно подготовленные supervision-индексы/маски/счётчики,
   сокращение повторных CUDA проверок и scalar reads. Внешний raw API сохраняет
   полную валидацию; внутренний проверенный путь защищён от мутаций/неверной
   идентичности. Метки не поступают в encoder/graph construction.
4. Сохранить reference path, диагностику и явный выбор runtime profile. Если
   уменьшение частоты диагностик необходимо, сначала раскрыть отличие в handoff.
   Не включать AMP/compile, менять batch/архитектуру или делать полный mmap-кэш
   в первый пакет. Workers/queue оставить4/5 для изолированного сравнения;
   параметризацию готовить только если она не расширяет первый пакет.
5. Подготовить воспроизводимый парный benchmark: прежний/новый trainer,
   no-attention модель, одинаковые initial model/optimizer/scheduler/scaler/RNG,
   records/shifts/batch boundaries. Предложенный screen:100warmup+500measured
   updates на arm; вся подготовка учитывается отдельно и в whole-arm time.
6. Тесты: raw-only граница, masked/zero-support heads, все12shifts, cache ownership,
   равенство loss/gradients/состояний, full resume, повреждённый подготовленный

   real-data/GPU benchmark только координатор после ревью и завершения15k.

Handoff: публичный API prepared/runtime, точная область ускорения, параметры
reference/new, фактически пройденные тесты, CPU vs pending GPU, команды будущего
benchmark и commit. Не заявлять ускорение по чтению кода или fixture wall time.

## Координатор и переходы

Координатор читает новые результаты, делает независимое ревью исходников и
существенные тесты; возвращает конкретные замечания в соответствующую задачу.
Интеграция — отдельный checkout, не live cloud source. Каждый конфликт общей
функции разрешается через согласованный интерфейс; исторические terminal records
и результаты не перезаписываются. Параллельность разработки не означает
параллельный GPU benchmark на текущей машине.

После текущего15k сначала удостовериться в его terminal status, сохранности
артефактов и отсутствии активного владельца GPU. Выполнить только прошедший
ревью bounded admission/сравнение старого и нового no-attention trainer.
Перед существенным запуском создать planned record, лимит времени/памяти и
изолированный output; сохранять завершённые и неудачные попытки. Не запускать
весь15k повторно только ради скорости. Ориентир первого screen1200updates
суммарно в двух arms, без сокращения исторического LR horizon. Любое расширение
этого screen отражать отдельным budget/record, а не бесконечными повторениями.
Не добавлять новые GPU VM/квоты или spot/MPS в этот первый пакет.

Только после проверки ускорения и C3-кода — короткий C3 GPU admission. Длительная
C3 campaign требует записанного пользователем бюджета; историческое80k другой
модели не является новым бюджетом C3. Если всё готово, сообщить готовность и
следующее конкретное сравнение. Нельзя объявить конечную эквивалентность или
выигрыш скорости без реальных измерений.
