## Восстановление позже

Скачать комплект кода в новую локальную директорию:

```bash
yc storage s3 cp \
  s3://music-critic-v2-b1g0sie8odv6h7khh28l/releases/20260916-temporal-main-r1/ \
  incoming/release/ --recursive
cd incoming/release
sha256sum -c SHA256SUMS
git clone -b main repository.bundle music-critic-v2
git -C music-critic-v2 bundle verify ../repository.bundle
```

На macOS вместо `sha256sum` используется `shasum -a 256`. Сначала проверить
наличие `COMPLETE.json`: он загружается последним, после остальных объектов.
`catalog.json` связывает код, исходные архивы и результаты с размерами и SHA256;
`source-status.json` содержит точные Git commits всех трёх веток.

1. Авторизовать официальный `yc` CLI. Скачать release-каталог
   `releases/20260916-temporal-main-r1/` и проверить контрольные суммы.
2. Восстановить Git: `git clone -b main repository.bundle music-critic-v2`.
   Fusion сохранён в bundle отдельно; см. [карту веток](BRANCHES_AND_RELEASES.md).
3. Скачать и восстановить подготовленный набор командой ниже. Скрипт проверяет
   receipt, части, каждый payload, допустимые имена и TRAIN/VALIDATION splits.
   Выбранная директория назначения должна отсутствовать; её родитель должен
   быть доступен для записи. Частичная неудачная распаковка не перезаписывается.
4. Исторические архивы распаковывать в отдельную пустую директорию. Части
   сначала соединить в порядке receipt и сверить полный хеш. Старые source
   snapshots не распаковывать поверх текущего checkout.
5. При другом корне данных изменить `--destination`: скрипт создаст производный
   `data-manifest.json` с новыми путями и `restore-receipt.json`, сохранив
   исходный манифест и SHA256 payload. Повторная проверка без распаковки —
   та же команда с `--verify-only`.

Из корня восстановленного репозитория, с Python3.12+:

```bash
yc storage s3 cp \
  s3://music-critic-v2-b1g0sie8odv6h7khh28l/data/prepared/58085b4e58e03f3a/ \
  incoming/prepared/ --recursive
python scripts/restore_training_data.py \
  --package incoming/prepared \
  --destination "$PWD/restored-data/prepared" \
  --expected-receipt-sha256 1904b052e663ccbdc18f49ce72ec119430e6c19ba8ff125d0b5d5d34dec54f15
```

Скрипту не нужны Torch/CUDA; он не запускает модель и не разбирает музыкальные
таргеты. Новый манифест здесь будет `restored-data/prepared/data-manifest.json`.

Object Storage используется для хранения; обучение читает локальный диск
будущей VM. Перенос не делает прежние GPU-gates действительными на другой машине.

Восстановление раннего Git bundle уже проверено именно после скачивания из
Object Storage: SHA256 совпал, все три ветки восстановлены, fusion-модули
отсутствуют в main и присутствуют в fusion-ветке. Полный подготовленный набор
также восстановлен и проверен локально. Это проверка переносимости файлов,
а не повторное GPU-обучение.

## Независимые параллельные обучения — 2026-09-16

Пользователь сообщил о гранте 18 000 руб. на этот проект и допустимом хранении
до 500 руб./месяц. Бюджет обучений и их число пока не выбраны.

Возможны отдельные GPU VM на каждый эксперимент либо отдельные GPU одной VM.
Первый вариант проще изолирует CPU/RAM, admission и supervisor. Для общей VM
нужно согласовать выбор GPU в тренере и физический GPU UUID/index в проверках:
в частности, memory probe сейчас вызывает nvidia-smi --id=0 и отклоняет другой
вычислительный процесс. Одной CUDA_VISIBLE_DEVICES без проверки мониторинга
недостаточно. Несколько обучений на одной GPU требуют отдельной адаптации и
измерения совокупной производительности, CPU/RAM/VRAM; свободная VRAM не
доказывает пропорционального ускорения. В существующем коде этот режим не допущен.

Каждому запуску нужны отдельные experiment ID, output/log/checkpoint paths и
проверенные resource bindings. Один неизменяемый набор в Object Storage может
быть источником для всех VM, но рабочие копии на дисках VM занимают место каждая.
Два одинаковых независимых запуска по T часов: последовательно 2T календарных
часов, параллельно около T, в обоих случаях 2T VM-часов при одинаковом runtime;
скорость расходования гранта при параллельном запуске удваивается. Фактическая
цена дополнительно зависит от дисков/IP и других ресурсов.

Живые GPU/vCPU/RAM квоты аккаунта пока не проверены. Документация указывает
нулевые GPU-квоты по умолчанию; это не утверждение о фактической квоте аккаунта.
Рекомендация для будущей работы: сначала один короткий зарегистрированный
прогон для времени/стоимости, затем два независимых эксперимента при подходящем
бюджете. Никакого обучения или платной VM этот разбор не запускает.
Источник: https://yandex.cloud/ru/docs/compute/concepts/limits
