# Почему облачный T4 медленнее RTX 3090

17 сентября 2026. Одинаковый короткий профиль reference temporal/C2 воспроизвёл
замедление облака: **1,304 против 0,612 с/шаг, в 2,13 раза**. Существенная часть
времени уходит на ожидание, подготовку и передачу структур данных между
процессами. T4 также дольше выполняет GPU-операции, но GPU большую часть
наблюдаемого интервала не исполняет kernels/memcpy/memset нашего процесса.

## Что сравнивалось

На каждой машине выполнены 310 обновлений: 100 прогрева, **200 для скорости**,
10 отдельно с CPU/CUDA profiler. Те же 620 draws, произведения, транспозиции,
порядок, batch=2, workers=4, pending=5, FP32, seed=17, dropout seed=17001,
горизонт LR=120k. Совпали source/data/implementation fingerprints и полный
draw-stream. Использован reference с прежним coalesced runtime, без prepared
оптимизации и без attention. Модель не менялась.

Это сравнение двух развёрнутых окружений, **не изолированный тест видеокарт**:

| | Сервер 3090 | Облако T4 |
|---|---|---|
| CPU | Intel Core i7-14700K | Intel Xeon Icelake, KVM |
| Видимые CPU | 28 logical CPU | 16 vCPU, гостевая топология 8 cores × 2 threads |
| Torch | 2.2.2+cu118 | 2.8.0+cu126 |
| PyG | 2.6.1 | 2.7.0 |
| Python | 3.12.8 | 3.12.11 |
| Средний обычный шаг | **0,6124 с** | **1,3040 с** |
| Обновлений в секунду | **1,6330** | **0,7669** |

Нельзя приписывать всю разницу CPU, GPU или версии Torch по отдельности.
100 шагов прогрева не означают полностью прогретый корпус: суммарно за
310 шагов было 26 cache hits/594 misses на 3090 и 41/579 на T4. Назначение
заданий воркерам зависит от планировщика; cache residency между хостами не
фиксировалась. Вытеснений из кэша не было на обоих хостах.

## Куда уходит обычный шаг

В таблице среднее время CPU-областей за 200 шагов без CUDA events/profiler.
Forward/backward включают запуск операций, синхронизацию и возможное ожидание
GPU; это **не чистое время GPU**. H2D — весь вызов переноса структуры графа.

| Область | 3090, с/шаг | T4, с/шаг |
|---|---:|---:|
| Ожидание результата очередного воркера | 0,2777 | 0,5921 |
| Распаковка и проверка батча в основном процессе | 0,0830 | 0,1832 |
| Перенос графа на GPU | 0,0195 | 0,0416 |
| Forward | 0,0760 | 0,1588 |
| Выравнивание таргетов и loss | 0,0744 | 0,1529 |
| Backward и диагностика градиентов | 0,0743 | 0,1584 |
| Optimizer | 0,0039 | 0,0098 |
| Весь шаг | **0,6124** | **1,3040** |

Ожидание очереди составляет **45,36% на 3090 и 45,41% на T4**. Оно означает
ожидание `future.result`: включает готовность воркера и доставку результата,
поэтому его нельзя считать только временем построения графа. Распаковка —
ещё около 14% шага. Даже идеальное устранение только ожидания очереди при
неизменной остальной работе даёт теоретически около 1,83×; это не прогноз
ускорения от увеличения числа воркеров.

Внутри воркеров за все 310 задач суммарно потрачено:

| Работа | 3090, с | T4, с | T4/3090 |
|---|---:|---:|---:|
| Подготовка и проверки | 329,97 | 743,23 | 2,25× |
| Сериализация | 122,91 | 251,87 | 2,05× |

Эти времена суммируются по параллельным воркерам и перекрываются с основным
процессом. Их нельзя прибавлять к времени шага. Тем не менее, они подтверждают
замедление CPU/data-path в облачном окружении. Причины внутри CPU, библиотек,
планирования и виртуализации этим тестом не разделены.

## Что показала отдельная GPU-трасса

Для последних 10 шагов независимо пересчитано объединение интервалов
`kernel`, `gpu_memcpy`, `gpu_memset`, без CPU-интервалов и двойного учёта
перекрытий. GPU user annotations, присутствующие в новой версии profiler,
не принимались за CPU-области шага.

| | 3090 | T4 |
|---|---:|---:|
| Активные GPU-операции, среднее на traced шаг | 0,0688 с | 0,1699 с |
| Их доля внутри CPU-областей 10 шагов | 11,80% | 12,67% |
| Число kernels за 10 шагов | 222 415 | 238 857 |

GPU-операции на T4 занимают примерно в 2,47 раза больше времени, но обе
машины исполняют десятки тысяч коротких kernels на шаг с большими промежутками.
Это согласуется с ограничениями подачи данных и запуска мелких операций.
Значения 11,80/12,67% — диагностическая доля записанной трассы нашего процесса,
**не средняя загрузка GPU всего обучения и не SM occupancy**. Profiler влияет
на выполнение, поэтому эти 10 шагов исключены из основного замера. Нельзя
переносить разницу GPU-времени этих шагов на 200 других и выдавать точное
процентное разложение причин замедления.

## Что делать на основании результата

1. Исправить дорогую подготовку/сериализацию и распаковку батчей. Prepared
   вариант из предыдущего эксперимента пока не использовать: он переносил
   дополнительные затраты в основной процесс и оказался медленнее.
2. Проверить 4 против 8 workers и согласованный prefetch на коротких одинаковых
   участках, с ограничением памяти. Сразу 16 workers не обоснованы: основному
   процессу тоже нужен CPU, а распаковка остаётся последовательной.
3. Изучить группировку мелких GPU-операций, копирований и CPU/GPU-синхронизаций
   с отдельной проверкой эквивалентности. Более дорогой GPU пока не выбран.
4. Новые варианты принимать только после короткого теста корректности и
   измеримого выигрыша; затем переходить к длительным attention-абляциям.

Эти следующие эксперименты ещё не запущены. Нынешний тест не измеряет качество
модели и не заменяет долгий прогон: один seed, один короткий участок. Запись
журнала с fsync происходит вне измеренного шага, но может влиять на prefetch;
условия одинаковы по коду, диски и окружения различаются. Проверка сохранила
original Torch/CUDA/PyG, зависимости не устанавливались.
