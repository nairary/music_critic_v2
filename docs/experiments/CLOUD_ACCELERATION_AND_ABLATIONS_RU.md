# Ускорение temporal-модели и параллельные абляции в облаке

Дата: 16 сентября 2026. Этап 9E: аудит и инженерный план. Авторизованный
`EXP-CLOUD-T4-TEMPORAL-15K-001` продолжает работу с четырьмя воркерами.
Этот документ не запускает новые обучения, не изменяет текущие параметры и
не утверждает измеренного выигрыша от ещё не реализованных оптимизаций.

Основная рекомендация: сначала сократить повторную работу в последовательной
части тренера, затем настроить подачу данных, после этого выбирать размещение
независимых запусков. Главные показатели — время и рубли на одинаковый объём
полезных обновлений, а для серии абляций — время завершения всей серии.

## 2. Конкретные затраты в коде

Указанные строки относятся к запущенному `177e514`; ссылки ведут к тем же
исходным модулям проекта. Наличие операции подтверждено чтением кода, её доля
в стеночном времени ещё требует профилирования.

1. **Повторная проверка графов на GPU.**
   `move_raw_graph_batch` делает deepcopy, перенос тензоров и полную валидацию.
   Локальный энкодер проверяет вход снова; проверка рёбер вызывает `.item()` и
   `torch.equal`, затем граф разбирается на произведения и проверяется повторно.
   Иерархическая принадлежность вычисляется в энкодере и ещё раз в BiGRU.
   См. [перенос](../../src/music_critic/experiments/analysisgnn/corrected_training.py)
   (606–617), [проверки](../../src/music_critic/graph/validation.py) (368–560),
   [энкодер](../../src/music_critic/models/encoder.py) (409–427),
   [BiGRU](../../src/music_critic/models/onset_bigru.py) (137–194).
2. **Служебные синхронизации loss.** В `corrected_supervised_loss` четыре
   явных `.item()` на голову: 72 чтения скаляров за шаг для 18 голов. Ещё
   синхронизации вызывают проверки масок/диапазонов. Для каждой головы отдельно
   считаются weighted CE для обучения и unweighted CE для диагностики.
   См. [loss](../../src/music_critic/experiments/analysisgnn/corrected_training.py)
   (484–540), [CE](../../src/music_critic/experiments/analysisgnn/training_policy.py)
   (338–371). Такие обращения препятствуют асинхронной работе CPU и GPU:
   [рекомендации PyTorch](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html).
3. **Повторная подготовка таргетов после forward.** На каждом шаге заново
   строятся словари, соответствия событий, точные временные значения и маски,
   хотя они зависят от графа и сдвига, а не от весов модели.
   См. [alignment](../../src/music_critic/experiments/analysisgnn/temporal_slices/alignment.py)
   (39–133).
4. **Частные кэши и тяжёлая передача.** Общие 8 ГиБ делятся на четыре LRU
   по 2 ГиБ; привязки произведений к воркеру нет. Восемь воркеров с прежним
   общим бюджетом получат по 1 ГиБ, что может увеличить число промахов.
   Воркер упаковывает весь граф и sidecar-словари в `pickle`-байты; главный
   процесс распаковывает и проверяет их. См.
   [campaign](../../src/music_critic/experiments/analysisgnn/temporal_slices/campaign.py)
   (101–208), [cache](../../src/music_critic/experiments/analysisgnn/temporal_slices/cache.py)
   (294–335).
5. **Очередь и неодинаковые произведения.** Пять заданий включают обрабатываемый
   моделью батч. Пополнение идёт после применения обновления. Длинный ранний
   батч задерживает выдачу уже готовых следующих. Порядок должен сохраняться;
   брать первый готовый батч для ускорения нельзя.

## 3. Порядок изменений

### A. Измерить этапы и убрать повторную работу тренера

Первый инженерный пакет должен добавить раздельные таймеры ожидания результата,
распаковки, H2D, forward, alignment/loss, backward/optimizer, checkpoint и
validation. Воркер сообщает hit/miss/eviction, время сборки, транспозиции,
валидации, сериализации и размер результата. Время GPU измеряется CUDA events
и коротким profiler trace; синхронизация после каждого участка не должна
искажать отдельный обычный замер полной скорости. Учесть разные размеры графов.

Затем сформировать проверенный подготовленный пакет:

- структура, принадлежность нот/долей/тактов, индексы последовательностей и
  неизменяемые степени узлов готовятся и проверяются на CPU;
- таргеты, маски, диапазоны и счётчики остаются отдельной supervision-частью;
  они не поступают в энкодер и не определяют исходный граф;
- соответствие выходным позициям проверяется по идентичности кандидатов;
- обычный интерфейс для внешнего raw MIDI сохраняет полную валидацию;
- быстрый внутренний интерфейс допускает только пакет с проверенной схемой,
  происхождением и владением тензорами. Мутация после проверки не допускается;
- проверки конечности обучаемых значений и корректности применённого шага
  сохраняются; диагностические обращения объединяются, где это возможно.

Первый вариант сохраняет FP32, weighted loss, порядок редукций и доступность
диагностик. Снижение частоты unweighted CE — отдельное явное изменение отчётности.
Готовая supervision-часть не является разрешением закодировать gold-метки в
признаки. Отложенные phrase/section и новые changes не входят в этот пакет.

### B. Настроить очередь и кэш

Предлагаемый последовательный screen: `4 workers / 5 pending` → `4 / 12` →
`8 / 16`, при одном FP32-коде и одинаковых батчах. Это кандидаты после проверки
памяти, а не готовые конфигурации. В текущем коде workers/pending/cache жёстко
ограничены; нужны операционные параметры и тесты.

Первое сравнение изолирует глубину очереди. Второе проверяет выбранную
конфигурацию целиком: при неизменных общих 8 ГиБ меняется объём кэша на воркер.
Размер очереди ограничивается также байтами: 16 консервативных резервов по
477102080 B — около 7,11 ГиБ только сериализованных данных, без рабочих копий.
Не считать свободную RAM в одном замере гарантией безопасности крупных графов.

Для серии абляций перспективнее постоянное хранилище **identity-графов** на
локальном SSD с общим read-only mmap/тензорами: один раз подготовить 1295 TRAIN
произведений и переиспользовать между seeds/запусками. Не начинать с 12 полных
копий для транспозиций. Каждый батч получает собственные изменяемые тензоры;
преобразования и маски проверяются для всех сдвигов, включая историческую
семантику агрегированных pitch-признаков. Часть общих массивов может быть
разделена между процессами только при доказанной неизменяемости.

До реализации полного кэша нужны его размер и время сборки. Окупаемость для
n запусков: `T_build + n × T_run_cached < n × T_run_current`, включая cold start,
перенос кэша и последующие проверки. Новый format/fingerprint получает новую
версию; старый кэш не перезаписывается. Для нескольких VM исходный пакет общий
в Object Storage, рабочая копия локальная каждой VM.

Компактная передача supervision/тензоров и pinned asynchronous H2D идут по
результатам таймеров. Ручной `pin_memory()` в главном потоке не гарантирует
выигрыша; требуется корректное владение буферами до завершения копии.
[PyTorch о передаче памяти](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html).

### C. Отдельно проверить численные оптимизации

AMP FP16 для допустимых частей энкодера с FP32 heads/loss и рабочим scaler —
перспективный кандидат для T4. Это новая численная политика: нельзя объявлять
её побитно эквивалентной текущему FP32 или смешивать с архитектурной абляцией.
Оба сравниваемых архитектурных варианта должны использовать одну политику.

`torch.compile` сначала применяется к небольшим тензорным блокам после удаления
Python-валидации из горячего пути. Графы переменного размера, scalar-ветвления
и поштучный GRU могут вызвать graph breaks/recompilation. Считать и compilation
time; проверять API именно Torch2.8. [Документация 2.8](https://docs.pytorch.org/docs/2.8/generated/torch.compile.html).

Перестановка линейной проекции до gather, объединение feature projections и
batched GRU могут менять округление/порядок backward. Это отдельные варианты,
как и изменение batch size, gradient accumulation, bucketing с новым порядком.
Для первой оптимизации сохраняем batch2 и исходный sampler/schedule.

Фиксированную validation-популяцию тоже можно заранее подготовить и подавать
параллельно. Частоту validation/checkpoint ради первого ускорения не менять.

## 4. Как проверять без длинных бесполезных обучений

Перед GPU-исполнением каждого существенного сравнения нужен новый planned
experiment ID. Текущий запуск и его артефакты остаются отдельным контролем.
Разработка, тесты и подготовка конфигураций возможны во время его работы;
GPU-benchmark запускать отдельно, чтобы не смешать нагрузки.

Предлагаемый первый screen после текущего15k: общий фиксированный начальный
checkpoint состояния, одинаковый sampler и 100 warmup + 500 измеряемых updates
на вариант, один повтор для отсева. Время старта/прогрева тоже сохраняется.
500 шагов достаточно для первичного измерения скорости на выбранном потоке,
но не для вывода о качестве модели или выборе архитектуры. Узкий profiler
window отделён от обычного benchmark. Победитель подтверждается на более
длинном потоке, охватывающем повторные попадания и вытеснения кэша.

Проверки для оптимизаций, сохраняющих численную политику: те же batch boundaries,
все12shifts, веса классов/маски/нулевая поддержка, loss/gradients/model/optimizer/
scheduler/scaler/RNG, sampler commit только после применённого шага, полный
resume после остановки. Проверить крупные и крайние графы, повреждённые пакеты,
мутацию/алиасинг кэша и остановку воркеров. Побитное равенство — критерий проверки,
а не обещание до запуска. Если оно нарушено, объяснить причину и классифицировать
вариант отдельно. Для AMP/compile дополнительно требуется оценка качества.

Выбор по двум раздельным метрикам: steady updates/s и полное время/стоимость
фиксированного объёма с подготовкой, validation, checkpoint и выгрузкой.
Практический ориентир для принятия усложняющей код оптимизации — хотя бы20%
выигрыша полного времени; увеличение в2раза остаётся целью, не прогнозом.

## 5. Параллельные абляции

### Фактическая квота

Quota Manager на момент аудита: T4 `limit=1, usage=1`; vCPU32/16; RAM128/64ГиБ;
networkSSD200/100ГиБ; T4i и A100 — limit0. API показал одну RUNNING VM.
Две отдельные T4 VM сейчас не помещаются в GPU-квоту. Нужна заявка на T4≥2;
для двух16/64 прочие перечисленные квоты достаточны впритык. Доступность
конкретной зоны квота не гарантирует. Заявки этим аудитом не отправлялись.

### Два процесса на одной T4

После оптимизации одного запуска сравнить `1 job` и `2 independent jobs` на
одной16/64 VM. У каждого собственные модель/optimizer/RNG/очередь, experiment ID
и output root; общими могут быть только проверенные read-only данные.
Считать сумму полезных updates/s и замедление каждого. Например, два процесса
по0,55 против одного0,70 дают совокупный выигрыш1,57×, хотя каждый медленнее.
Это пример арифметики, не прогноз. Если один ускоренный процесс уже насыщает
GPU, совместное исполнение может перестать быть выгодным.

До такого теста нужен управляющий процесс всей VM: остановка машины только
после завершения/выгрузки всех назначенных заданий. Сегодня
`scripts/run_cloud_temporal.py:109–141` останавливает VM после одного дочернего
run. Нельзя просто запустить две копии обёртки. Проверки чужих CUDA-процессов
должны учитывать явно допущенные процессы двух экспериментов, а не отключаться.
Нужны совокупная memory admission, отдельные лимиты/журналы и тест завершения
первого job при работающем втором. Пик1,84ГиБ из короткого окна — не бюджет VRAM.

MPS — следующая отдельная проверка после обычного совместного исполнения.
Он позволяет перекрывать вычисления разных процессов, но усложняет учёт и
изоляцию ошибок. [NVIDIA MPS](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html).
Для независимых абляций DDP не является первым решением: он предназначен для
совместного обучения одной модели, а нам нужны отдельные модели.

### Две VM и RTX3090

После увеличения квоты сравнить две T4 8/32 с двумя процессами на одной16/64.
Две VM дают изоляцию и сокращают календарное ожидание; при одинаковой скорости
каждого job они сами по себе не уменьшают число оплаченных VM-часов.
T4 8/32 требует отдельной проверки памяти полного потока, а не экстраполяции
с нынешних12ГиБ host usage. CPU только4/16 — более тесный вариант и не первый
кандидат для текущего конвейера с четырьмя воркерами.

3090 оставить отдельным execution profile для разработки/длинных повторов:
один код и научный config, отдельные worker/cache/device/budget параметры.
Архитектурное сравнение не должно ставить контроль только на3090, а вариант
только наT4 с другой точностью/версией библиотек. Нужен контроль в каждой
существенно отличающейся среде либо явно историческая интерпретация.

проверенные checkpoint uploads, атомарный указатель последнего целого состояния,
ограниченные повторы с учётом бюджета, корректные continuation IDs и тест
остановки всей VM. Не рассчитывать на финальную выгрузку после сигнала остановки:
штатное окно завершения ОС —30секунд.
[Условия прерываемых VM](https://yandex.cloud/ru/docs/compute/concepts/preemptible-vm).

Текущие20h/22h пределы относятся к15k-проверке: их нельзя без пересчёта перенести
на80k, который при нынешней условной скорости длиннее. Полный lifecycle и
автовозобновление дают экономию расходов; это не ускорение вычислений за секунду.
