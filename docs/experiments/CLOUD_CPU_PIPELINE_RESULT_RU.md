# Ускорение CPU pipeline на облачной T4 — 17 сентября 2026

**На одном облачном окружении `pipeline8` сократил время обновления с
1,379 до 0,819 с: ускорение 1,684×, на 40,6% меньше времени.**
`pipeline4` дал 1,152 с/шаг, ускорение 1,197×. Все три варианта сохранили
точное совпадение loss и нормы градиента на 300 шагах, а также fingerprints
начального и конечного полного состояния. Benchmark и независимый импорт
завершены; native gate новой интеграции в TRAIN также прошёл.

## Протокол и изменения

Одна T4, 16 vCPU Intel Xeon Icelake под KVM, 64 GiB RAM;
Python 3.12.11, Torch 2.8.0+cu126, PyG 2.7.0. Окружение и библиотеки между
вариантами не менялись. Исходники benchmark зафиксированы в commit
`c033f1d1db3980ce51051e9387a33247790f0900`, ветка
`codex/cpu-pipeline-20260917`.

В каждом варианте выполнены **100 прогревочных + 200 измеряемых обновлений**,
всего **900 updates / 1800 draws**, batch=2. Каждый начинался с одинакового
состояния модели и RNG, с новым пулом и пустыми worker-кэшами. Совпали записи,
транспозиции, порядок и границы батчей; покрыты все 12 shifts. Сохранены
temporal/C2 без attention, coalesced FP32 update, seed=17, dropout seed=17001,
исходное расписание LR с горизонтом 120k, loss, masks и историческое поведение
транспозиции. Это повтор одного и того же 300-step участка, а не обучение
одной модели на 900 последовательных шагах.

| Вариант | Workers / pending | Подготовка и передача |
|---|---:|---|
| `reference4` | 4 / 5 | Исходная проверка CPU payload, Torch storage pickle, полная повторная валидация canonical piece |
| `pipeline4` | 4 / 5 | Быстрый обход CPU payload, private packed tensor IPC, пропуск уже выполненной canonical-проверки в authenticated loader |
| `pipeline8` | 8 / 9 | Тот же набор изменений, больше параллельных workers и заданий в очереди |

Packed IPC сохраняет значения, dtype, shape и метаданные PyG; принимающая
сторона владеет отдельными CPU-буферами. Публичная полная валидация, проверка
исходных байтов, принадлежности TRAIN и построенных графов сохраняются.
Общий accounted cache budget во всех вариантах — **8 GiB**, по 2 GiB на
worker при четырёх процессах и по 1 GiB при восьми. Это не предел всего RSS:
рабочие объекты, decoded batches и копии IPC требуют дополнительной памяти.
Лимит сериализованных pending reservations вырос с 2,22 до 4,00 GiB.

## Скорость и оставшиеся затраты

Основная скорость пересчитана из 200 измеряемых строк журнала каждого варианта.

| Метрика | `reference4` | `pipeline4` | `pipeline8` |
|---|---:|---:|---:|
| Время 200 обновлений, с | 275,791 | 230,461 | 163,726 |
| Среднее время обновления, с | **1,378955** | **1,152305** | **0,818628** |
| Обновлений/с | 0,7252 | 0,8678 | 1,2216 |
| Ускорение к reference | 1,000× | 1,197× | 1,684× |
| Снижение времени к reference | — | 16,4% | 40,6% |
| Полный вариант с прогревом и подготовкой, с | 419,165 | 351,089 | 261,799 |

Среднее wall-время именованных участков на измеряемых шагах:

| Участок, с/шаг | `reference4` | `pipeline4` | `pipeline8` |
|---|---:|---:|---:|
| Ожидание worker/доставки результата | 0,6335 | 0,4306 | 0,0730 |
| Распаковка и проверка в основном процессе | 0,1942 | 0,1817 | 0,1854 |
| Перенос графа (`h2d`) | 0,0430 | 0,0424 | 0,0424 |
| Forward | 0,1590 | 0,1575 | 0,1567 |
| Alignment/loss | 0,1562 | 0,1525 | 0,1560 |
| Backward и диагностика градиентов | 0,1611 | 0,1563 | 0,1593 |
| Optimizer | 0,0100 | 0,0097 | 0,0103 |
| Область `full_step` | 1,3785 | 1,1518 | 0,8045 |

Основной выигрыш — меньше ожидания результата очередного worker. Интервалы
могут перекрываться; CUDA events выключены. Это wall-время CPU-областей,
включающее запуск операций и синхронизации, а не чистое время GPU или PCIe.
`full_step` заканчивается до commit очереди и записи внешнего тайминга;
поэтому основной показатель с/шаг немного больше этой области.

Суммарное время всех workers за 300 батчей:

| Работа, с | `reference4` | `pipeline4` | `pipeline8` |
|---|---:|---:|---:|
| Подготовка и проверки | 752,64 | 696,44 | 709,50 |
| Сериализация вместе с проверкой CPU payload | 248,09 | 88,99 | 89,27 |
| Cache hits / misses | 25 / 575 | 27 / 573 | 13 / 587 |
| Вытеснения из кэша | 0 | 0 | 5 |

Эти worker-времена суммируются по параллельным процессам и перекрываются с
основным процессом. Прибавлять их к времени шага нельзя. Короткий участок
остаётся преимущественно холодным даже после 100 шагов прогрева; поведение
кэша на полном корпусе и в длительном обучении этим замером не установлено.

После перехода на восемь workers заметны последовательная распаковка/проверка
около 0,185 с/шаг и работа forward/loss/backward. Простое дальнейшее увеличение
числа workers уже не устраняет эти затраты. Подготовка графов внутри workers
тоже остаётся дорогой: около 2,3 с на батч суммарного worker-времени.

Отдельный CPU cProfile на **предыдущем reference source**, без optimizer
updates и без CUDA, локализовал ещё один кандидат: fingerprint больших
sidecars. На восьми холодных батчах он занял 12,30 с из 57,40 с профилированной
работы; 10,84 с пришлось на предварительный обход `_reject_non_finite_json`
с построением диагностических путей. Этот участок сохранился в c033f1d.
Следующий узкий вариант — уменьшить этот повторный обход, сохранив точные
canonical bytes/hash и прежние ошибки невалидного ввода. Пока это предложение,
а не измеренное ускорение. Старые 13,68 с `_assert_cpu` на тёплом профиле уже
адресованы новым guard; их нельзя считать остаточными затратами pipeline8.

## Границы выводов и связь с прежними результатами

Это **один фиксированный порядок** `reference4 → pipeline4 → pipeline8`,
один seed и один короткий участок. Пакет изменений pipeline4 не разделён на
отдельные ablation: нельзя приписать весь выигрыш одному codec или validator.
При переходе pipeline4 → pipeline8 одновременно меняются workers **4 → 8**
и pending **5 → 9**; их эффекты отдельно не измерены. Планировщик также меняет
распределение записей по worker-кэшам. Статистическая значимость, скорость
длительного обучения и улучшение качества модели не заявляются.

Ранее [сравнение T4 и 3090](HARDWARE_PROFILE_T4_3090_RU.md) показало
1,3040 против **0,612351 с/шаг**. На сервере 3090 были Core i7-14700K,
Torch 2.2.2+cu118 и PyG 2.6.1; в облаке — Xeon/KVM и другое программное
окружение. Подготовка и сериализация в облаке были примерно вдвое медленнее,
но это не изолированное сравнение CPU или GPU. Новый результат 0,818628 с
численно остаётся примерно в 1,337× выше прежнего 3090; **замеры не одновременны,
а pipeline различается**, поэтому это ориентир, не новый парный тест машин.

Предыдущий [prepared benchmark](CLOUD_T4_PREPARED_BENCHMARK_RU.md) дал
отрицательный результат: 2,527 против 1,398 с/шаг, замедление 1,807×.
Его дополнительная подготовка и копирование в основном процессе сохраняются
в истории как отдельный неудачный подход. Нынешний benchmark использует
coalesced runtime во всех вариантах и не реабилитирует `prepared_v1`.

## Проверка, ресурсы и допуск TRAIN

Независимый импорт подтвердил все 900 строк applied updates, общий draw-stream,
точное совпадение 300 пар loss/gradient norm и fingerprints шести частей
начального и конечного состояния: model, gradients, optimizer, scheduler,
scaler, RNG. Проверены source/data/implementation bindings, 25 файлов архива
и все producer artifact hashes. Импорт не загружал checkpoint tensors и не
исполнял импортированный код; новых обновлений модели при анализе — 0.

Resource guard завершился с exit code 0: 1037,68 с общего времени,
выборочный пик GPU 1820 MiB, минимум доступной RAM около 49,5 GiB,
swap 0. Это выборочные наблюдения короткого benchmark, не worst-size admission.
Evidence выгружены; после benchmark Cloud API подтвердил STOPPED, диск сохранён.
VALIDATION использовалась только как membership metadata; её payload/inference
и TEST не использовались по связанным с исходниками отчётам. OS access trace
не выполнялся. Legacy не использовался.

Интеграция выбранного пути в настоящий TRAIN находится отдельно:
`codex/cpu-pipeline-training-20260917`, commit
`c4ddd56f3936701f3551b410ca9c7d27647030b2`.
Явные параметры — `runtime_profile: coalesced_reference`,
`cpu_pipeline: pipeline8`; прежние defaults автоматически не менялись.
Execution fingerprint связывает профиль с gate и полным checkpoint;
resume требует того же source/profile и заново строит disposable queue/cache.
**109 synthetic CPU-тестов прошли:** 29 за 7,42 с и 80 за 26,18 с,
по одному существующему PyG warning в каждом запуске. Проверены interrupted
TRAIN/resume обоих packed presets, отклонение изменённого профиля и cleanup.

**Native gate TRAIN-интеграции прошёл:**
`EXP-CLOUD-T4-CPU-PIPELINE-GATE-001`, **32 updates / 64 draws** за 165,62 с.
Все 12 shifts совпали с coalesced control; после полного checkpoint на шаге 2
новая очередь воспроизвела точное состояние непрерывного обучения до шага 4.
Проверены source/data/execution bindings, hashes всех producer artifacts и
37 файлов архива. Checkpoint при локальном импорте не загружался.
109 CPU-тестов интеграции дополнительно прошли на T4 за 104,26 с
(одно прежнее предупреждение PyG); 9 тестов launch/export glue прошли локально.
Выборочный пик GPU gate — 1260 MiB, swap growth 0.

После экспорта Cloud API подтвердил **STOPPED**, диск сохранён.
Таймер дедлайна оставался активен до завершения текущего запуска; его автозапуск
на следующем включении отключён, чтобы просроченный таймер не останавливал
будущие эксперименты. Длинное обучение не запускалось.
Worst-size memory admission остаётся отдельной проверкой перед длительным
обучением: короткий throughput-screen и этот gate не доказывают ресурсную
устойчивость на самом большом батче. Механизм attention здесь не проверялся.
