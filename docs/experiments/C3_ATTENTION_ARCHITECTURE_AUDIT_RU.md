## Ограничения, подтверждённые кодом

**Порядок.** Первый slice-query содержит только признаки времени/метра.
Он получает музыкальные значения уже контекстуализированных нот/долей/тактов.
Во втором проходе query уже зависит от своего собранного созвучия, но свежие
музыкальные сообщения соседних slices приходят одновременно с выбором нот.
Они не могут изменить этот выбор до следующего прохода. Новый цикл
`ноты → созвучие → контекст соседних созвучий → повторный выбор нот`
не завершается в двух синхронных слоях. Глобальный контекст base уже есть:
утверждение «модель не видит контекста» было бы неверным.

**Типы сообщений.** Attention выбирает внутри starts/holds/ends, после чего
результаты разных типов складываются (`c3_attention/model.py:133`). Отдельного
динамического выбора между типами нет. V-проекции различаются, поэтому нельзя
считать их численное влияние одинаковым. Начала/удержания/окончания раздельны
в topology (`temporal_slices/graph.py:160-167`); окончания не объявлены звучащими.

**Контекст событий.** В графе есть только next/rev_next для соседних slices
(`graph.py:192-193`). По каждому направлению один сосед, поэтому attention
там не применяется: softmax одного значения всегда1. Нет окон на1–4такта,
relative edge bias или прямой новой связи далёких событий.

**Память нот.** Следующий проход читает обновлённые note-состояния. Отдельной
сохранённой памяти первоначальных нот с повторным cross-attention нет.

**Блок.** Есть relation-specific V, GELU, dropout0.1, residual и LayerNorm.
Нет отдельного W_O/FFN attention-блока и attention-dropout. Это осознанная
минимальная абляция, не само по себе ошибка. Softmax может подавлять полезные
компоненты созвучия; случилось ли это в обученных весах, пока не измерено.

**Уточнение прежних объяснений.** C2 уже получал onset_qn/duration_qn и
положение в такте (`graph/builder.py:648-653`), а ноты получали контекст своей
дорожки (`models/hierarchy.py:997-1007`). Temporal добавил явные события и
связи атак/удержаний/окончаний, а не впервые дал время. Track-узлов нет именно
в добавленной temporal-ветке; нельзя говорить, что дорожки полностью исчезли.
Дорожка также не тождественна самостоятельному музыкальному голосу.

## Предпочтительные отдельные эксперименты

| Вариант | Вопрос | Приоритет |
|---|---|---|
| 3 прохода×128, mean и attention как пара | Поможет ли ещё один цикл новой slice-информации? | Первый архитектурный тест |
| Mean + управляемая attention-поправка | Полезно ли сохранить вклад всех нот при выборочном уточнении? | Отдельная следующая ось |
| Gate между starts/holds/ends/context | Нужно ли динамически выбирать тип сообщения? | После анализа поведения |
| Read notes → event context → re-read preserved notes | Нужен ли явный последовательный цикл вместо одинаковых GNN-раундов? | Основное дальнейшее направление |
| Метрические окна/relative timing bias | Не хватает ли доступных соседей и временных отношений? | Отдельно от глубины |
| Ширина128→192/256 | Ограничивает ли ёмкость уже работающий путь? | После порядка вычислений |

Один широкий синхронный слой не реализует многошаговую зависимость. Один
составной блок из read/context/re-read реализует её, но содержит три операции.
При трёх слоях промежуточный второй слой должен обновлять bar: нынешний
финальный его исключает. Простое добавление слоя после него не даёт пути
`note0→slice1→bar2→slice3`. Mean×3 нужен, чтобы отделить пользу глубины от
пользы внимания. Больше голов при фиксированной128 не увеличивает ширину.

Возможная поправка: `message = mean + g * (attention - mean)`.
Не ставить одновременно g=0 и нынешний zero-Q: attention=mean, обе ветви
получат нулевой стартовый градиент. Малый ненулевой g при zero-Q/random-K
сохраняет начальный mean и допускает обучение Q. Это требует отдельного теста.

Перед следующим долгим запуском полезна диагностика завершённого checkpoint:
нормы Q/K и градиентов, распределение количества соседей, entropy attention
при>=2соседях, отличие от mean, величина сообщений разных связей, различия
голов и классов. В этом аудите checkpoint не загружался, attention entropy и
oversmoothing/oversquashing не измерялись; причина наблюдаемого F1 неизвестна.
500steps годятся для механики/скорости, не для отбраковки качества архитектуры.
Сравнивать отдельно одинаковые updates/draws и wall time; новый бюджет здесь
не назначен. Batch, loss, targets, data и LR не менять одновременно с блоком.

## Связь с исследованиями

- [Di Giovanni et al., ICML2023](https://proceedings.mlr.press/v202/di-giovanni23a.html):
  ширина, глубина и topology влияют на передачу дальнего сигнала по-разному.
  Это обоснование проверки связей, не диагноз oversquashing нашей модели.
- [Perceiver, ICML2021](https://proceedings.mlr.press/v139/jaegle21a.html):
  повторное чтение входа компактными латентами — известный подход.
  Предложенный музыкальный read/context/re-read ещё надо проверить.
- [GraphGPS, NeurIPS2022](https://arxiv.org/abs/2205.12454): сочетает локальную
  передачу сообщений, глобальное внимание и позиционные/структурные признаки.
  У нашего base уже есть контекстный Transformer; новая гипотеза относится
  именно к последовательности точных событий, а не к добавлению контекста с нуля.
