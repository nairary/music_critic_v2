# Exact temporal graph and isolated training campaign

Phase9E opt-in implementation, 2026-09-15. Module:
`music_critic.experiments.analysisgnn.temporal_slices`. This is a new model
class and campaign path; historical C2/fusion/MMoE implementations, graphs,
checkpoints and evidence retain their contracts.

## Implemented computation

The unchanged C2 raw six-type graph passes through its local GNN, hierarchical
Transformer and onset BiGRU. A separate graph stage then adds exact temporal
slices: the union of raw note attacks, releases, and beat starts/ends.
The original `onset` nodes still mean attacks only. No gold chord boundaries,
theory labels, target masks, staff or voice annotations create slice nodes.

Each slice has its own 128-dimensional state. Fourteen directed relation types
connect notes to slices as attack, strictly held interior, or release; raw
onsets to coincident slices; beats/bars to their slices; and successive slices.
Every relation has its reverse. Zero-length grace notes have attack/release
edges and no held edge. Distinct notes remain distinct, even at the same pitch
and time. Sustained-note links are generated by exact interval search, with no
silent cap, subsampling or rounding.

Two relation-aware residual message-passing rounds use a separate linear map
per relation, relation-wise degree means, sum across relations, GELU, dropout
0.1 and per-type LayerNorm. The first updates note/onset/beat/bar/slice; the
second updates note/beat/slice, the downstream prediction types. Final-round
onset/bar updates would have no downstream consumer and are deliberately absent.
First-round parent updates feed the second-round slices. This is a late temporal
graph stage; it does not retrofit a seventh node type into the production
encoder, and does not send its new states back through the song/track Transformer.

New features encode phase within the raw beat, position in the metric bar
including pickup offset, beat index, meter numerator/denominator, adjacent
time gaps, attack/release/boundary flags, owner availability and pickup/incomplete
bar flags. These are relative musical coordinates. Exact `Fraction` timing
determines identities, ordering, ownership and edges; floats appear only at the
neural feature boundary. The unchanged base C2 still has its existing features,
including absolute-time features; the whole model is not claimed origin-invariant.

Half-open spans own their start but not their end; the terminal end belongs to
the last span. A slice in a gap or outside a span has explicit missing-owner
flags and no invented parent. Beat/bar structure is retained.

### Timing and information-flow clarification — 2026-09-16

The two input paths do not mean that original C2 receives beat-quantized notes.
Its raw note features already include onset, duration and position within the
bar; its graph also includes note-to-beat `active_at` links. The neural time
features are floats, while canonical topology uses exact rational timing.
An offset is recoverable from onset plus duration; the temporal extension makes
that boundary an explicit slice with an `ends` relation. Old harmonic outputs
were routed to beats. New exact slice states and slice-level outputs change the
representation and readout, not the existence of original note-time evidence.

For every note, one edge marks its start, another its end, and `holds` edges
connect it to every existing slice strictly between those endpoints. Slices are
the union of all notes' attacks/releases and beat boundaries. Thus changes in
other notes during a sustained note are represented without sampling every
instant. Between adjacent slices there is no modeled note attack/release;
continuous controllers, audio decay and raw events absent from this union are
not implied by this coverage. At an ending slice, `ends` describes the boundary,
not continued post-boundary activity; zero-duration notes have both boundary
roles and no interior. Raw metric coordinates remain separate from wall time.

This late extension preserves a tested C2 path and isolates the changed graph
stage operationally; it does not prove early integration would be worse or
isolate a timing-only scientific effect. Early integration would require adding
slice handling to the original node schema, encoder, batching and checkpoint
contracts. Current two stages do not re-enter the original global Transformer.

Proposed attention first selects neighbors within each relation; existing
relation-specific learned projections remain. Their matrices may already scale
relation contributions, but there is no explicit receiver-dependent gate between
relation summaries. With one neighbor in a relation, its softmax weight is one.
A second attention/gate over relation summaries is a separate proposal.

Current two rounds already revisit evolving node states. The later repeated-read
proposal specifically retains a note-memory bank during a forward pass, inserts
explicit context exchange between temporal/bar states, then queries the retained
note bank again with updated queries. Original C2 states already carry broad
context; this is a new refinement path rather than first access to future events.
Early note features as an additional memory source are a further independent
choice. Existing18-task losses can train such a path; named preparation or
resolution predictions would require their own justified targets/evaluation.
Attention and repeated-read variants are not implemented by this clarification.

The terms note memory, event states and bar summaries refer to latent encoder
states, not outputs of any classification head. The immediate note-memory
candidate is `base.encode(...).fused.embeddings["note"]`, one row per raw note.
Slices start from the14-feature projection and receive typed graph messages.
Bar states already exist in `encoded["bar"]`; updating bar summaries from refined
slices and exchanging them across bars is part of the proposed later context
block. Retaining a bank for repeated reading does not mean freezing its encoder
parameters during training. Q/K/V would be learned projections of these latent
states; the existing18 classifiers operate downstream. No predicted or gold
chord/key label is needed to create these memory banks or raw event/bar nodes.

### Proposed track-conditioned temporal refinement — 2026-09-16

User suggests processing each track's events and attending between tracks.
This is a further candidate, not an implemented model or a replacement for the
selected first attention-on-existing-relations experiment. C2 retains individual
note/track rows and note-to-track ownership. Its coarse sequence contains SONG,
all bar tokens and all track tokens; self-attention allows interaction between
tracks already, and each note receives its owner's track context. Track pooling
summarizes the whole track rather than a track-by-time sequence. Temporal slices
currently gather notes across tracks without separate track-by-slice states.

A possible extension creates raw-derived `(track_id, slice_time)` states,
gathers each track's starting/held/ending notes, exchanges context along time
within each track and between tracks at aligned moments, then retains separate
track states while building the ensemble state for global harmonic heads.
Updated owner-track states could also feed note heads or later note rereading.
Track-by-bar summaries are a coarser alternative for context, not the same
resolution. Active/silent availability, exact sustained-note membership, batching
and variable track counts need explicit handling. No gold voices, track roles
or chord boundaries should create these nodes. The18 existing losses could
supervise an internal refinement; per-track harmonic labels must not be invented
by copying the global harmony target onto each individual part.

Splitting C2's contextual note rows by track does not undo prior cross-track
mixing; truly isolated early track processing would require a separate early
path. A raw track is not necessarily one musical voice: polyphony may occupy a
single track, and source partition choices affect usefulness. This proposal
establishes no benefit for voice leading or counterpoint without evaluation.

## Outputs and supervision

The same eighteen head MLPs, class vocabularies, frozen class weights and
`mean(primary) + 0.25 * mean(auxiliary)` loss are reused. No fusion or MMoE is
added. Initialization constructs C2 before new layers, preserving its initial
weights for the same Torch seed.

- Twelve harmonic heads predict for all slices and all raw beats, in distinct
  namespaces. After prediction, an eligible target uses its exact slice first;
  if absent, it may use its existing harmonic-event-to-beat relation.
- Cadence predicts on slices, with no beat fallback.
- The five note heads remain indexed by original note identity, with updated
  note embeddings from the temporal graph.

All output candidates exist before reading targets. Source-unavailable, masked,
unknown-class and unaligned targets remain invalid. Native target rows,
including simultaneous conflicts and repeats, are retained. Sidecar hashes,
record/component/entity IDs and per-row route diagnostics accompany alignment.
`common_support_masks` intersect new eligibility with historical raw-entity
alignment. The campaign reports this shared support separately from expanded
support, including newly covered cadence positions. Checkpoint selection uses
the common-support mean macro-F1 over the eight primary heads. Expanded-support
metrics are retained as a separate result, not substituted into historical
comparisons.

The prototype exposes `transpose_temporal_batch` for explicitly directed raw
transforms. The controlled campaign instead calls `transpose_temporal_historical`,
which delegates to the exact existing C2 `transpose_raw_graph_batch` path and
its canonical forward direction. This preserves the known historical stale
track pitch summaries: note pitch, pitch class, octave and track-relative pitch
follow the original transform, while track-level pitch summaries are not
recomputed. No separate transposition repair is mixed into this experiment.
Temporal topology, exact slots and relative metric features remain unchanged.
The same applied shifts are passed to target alignment. Training loss preserves
the existing supported-class masks. An empty candidate bank uses a masked
loss-only sentinel, never an extra inference node or a negative target.

## Accelerated CPU preparation

`cache.py` adds `TemporalSliceIdentityCache@1.0.0` and
`TemporalSliceCPUPayload@1.0.0`, separate from all historical graph caches.
`FrozenTemporalRecordLoader` reads authenticated canonical TRAIN exports and
their original sidecar JSON bytes. It gates membership before payload access,
checks source identities on cache hits, and rehashes changed files. Campaign
startup/resume authenticates the declared warm files against the frozen data
manifest. The TRAIN-only cache cannot serve VALIDATION or TEST; validation uses
the separate explicit uncached reader. Neither path reconstructs missing warm
exports automatically.

Each cache entry contains one identity graph, exact readout slots and immutable
sidecar bytes. Entries are private; collation creates caller-owned tensors and
metadata, and repeated record occurrences receive independent decoded sidecars.
The historical C2 transform is applied after collation. Twelve transposed graph
copies are not retained. IPC represents each exact time as canonical integer
numerator/denominator pairs; deserialization checks the dedicated schema,
sample boundaries and topology before model use.

Four spawned CPU workers prepare fixed batches of two ahead of GPU execution.
The aggregate accounted cache budget is 8 GiB, partitioned into four 2 GiB LRUs.
Oversized entries bypass retention instead of exceeding their cache budget.
There are at most five submitted, uncommitted jobs; each serialized payload is
capped during serialization at 477,102,080 bytes. Thus pending serialized payload
reservations total at most 2,385,510,400 bytes, approximately 2.22 GiB. These are
retained-cache and payload limits, **not an RSS bound**: worker construction,
defensive copies, decoded sidecars, IPC copies, parent batches and GPU tensors
need separate memory admission. Cache hits and coverage are observations, not
a guarantee that the entire corpus fits in each worker.

Workers check their implementation identity and do not create a CUDA model.
Preparation is RNG-free. Results are delivered in frozen job order; only an
applied optimizer update commits the sampler cursor. A failed or interrupted
attempt discards speculative jobs. Worker shutdown is bounded and can terminate
only processes created by this pool. CPU library thread limits must be exported
before Python imports for the native launcher.

## Full checkpoints and experiment budget

`TemporalSliceTrainingCheckpoint@1.0.0` stores model state and contract, per-module
training modes, AdamW state, learning-rate scheduler, scaler, the committed
full-orbit sampler position, all training RNG domains, validation/best-selection
progress, source/data/environment bindings and state fingerprints. Checkpoint
publication is immutable and load uses restricted tensor-safe deserialization.
Schema, integrity, configuration and cursor checks precede restoration; a
restoration error rolls back the caller's components and RNG.

The cache and worker queue are deliberately absent from the checkpoint. Resume
rebuilds them cold from the restored committed draw position, without advancing
past merely prefetched jobs. A checkpoint can retain a pending validation, which
must complete before the next training update. Exact continuation is an admitted
same-runtime claim; it is not a promise of identical arithmetic across different
PyTorch versions or devices.

The selected campaign is ordinary C2 plus temporal slices, without fusion or
MMoE: 80,000 applied updates from scratch, batch size 2, seed 17, and the original
120,000-update learning-rate schedule. It reuses the frozen full-orbit record/
shift stream, 18 heads, vocabularies, source masks and class weights. Full
checkpoints are written every 1,000 updates and validation runs every 5,000.
The budget and implementation do not by themselves authorize bypassing the
native equivalence and memory gates.

## Isolation and evidence

Schemas `RawTemporalSliceGraph@1.0.0`, `C2TemporalSliceModel@1.0.0`, and
`TemporalSliceTargets@1.0.0` are separate. A full graph fingerprint includes the
base graph, extension features, node IDs, sample boundaries, edges and schema.
The original six-type validator remains strict. Existing model state dictionaries
cannot be loaded directly as complete temporal checkpoints. Historical cache
formats and dispatchers remain unchanged; only the isolated temporal campaign
admits this variant.

The package supplies a trainable model, post-prediction alignment, transposition,
reference and accelerated update paths, cache/worker preparation and full
checkpoint continuation. Synthetic tests cover gradients, batching, exact-time
routing, masks, fallback, baseline initialization, all twelve transpositions,
cache ownership, source admission, ordered commits and state/RNG continuation.
`EXP-TEMPORAL-SLICE-CPU-001` adds four hash-bound TRAIN examples with CPU
forward/backward checks and no optimizer steps. See the
[Russian technical report](experiments/TEMPORAL_SLICE_CPU_RU.md).

`EXP-TEMPORAL-SIZING-002` completed all 1,295 TRAIN graph builds in 337.416 seconds:
1,216,363 temporal slices and 20,978,532 directed extension edges in total. This
establishes full-TRAIN construction coverage. The measured graph tensor sizes
exclude model activations, Python objects, sidecars and IPC copies; they do not
establish GPU or host-memory readiness for training.

## Native admission status

The first native attempt, `EXP-TEMPORAL-GPU-GATE-001`, completed exact reference/
accelerated comparisons over all twelve shifts, then failed while saving
checkpoint metadata because of a PyTorch `TorchVersion` compatibility issue.
That attempt remains preserved. `EXP-TEMPORAL-GPU-GATE-002` subsequently
passed all32updates including exact full checkpoint continuation after normalizing
the Torch version metadata to builtin `str`. `EXP-TEMPORAL-GPU-MEMORY-002`
passed five largest-graph forward/backward jobs:2.41GiB peakallocated,
2.61GiB reserved, with a16GiB limit and host-memory guard. Model runtime source
matches the admitted gate byte for byte. A fresh80k campaign is now running;
throughput is observed from its journal and is not inferred from these correctness
tests. See [launch evidence](experiments/TEMPORAL_C2_LAUNCH_RU.md).

Quality improvement remains an experimental question. The larger graph retains
same-time annotation conflicts and the rare coarse fallback. Degree averaging
can still dilute note identity; the new timing resolution alone does not prove
voice-leading or harmonic understanding. Long held notes add edges at every
intermediate raw slice; largest-work memory needs explicit admission.

The preceding MMoE run was stopped at 47,186 observed updates after the user's
authorization; its best model at 40k and full checkpoint at 47k were retained.
This is experiment prioritization, not proof that MMoE could never improve later.
No legacy logic or new dependencies are used by the temporal implementation.
