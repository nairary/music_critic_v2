# Как проверять обучаемую иерархию нот, гармоний и процессов

27 октября 2026. T08, исследовательская рекомендация. Это выбор кандидата для следующего протокола, не установленное превосходство и не запуск обучения.

## Выбор

Первым проверить **рекуррентную сеть над типизированным графом участников и событий**, с вниманием в духе Heterogeneous Graph Transformer (HGT), сохраняемыми состояниями всех уровней и повторными проходами снизу вверх и сверху вниз.

Целевой путь: наблюдаемые ноты/время → кандидаты h/H/P → совместно уточняемые состояния → предсказания границ, свойств и адресных связей. C3 служит инициализацией нескольких уровней, затем возможен live end-to-end gradient. NBFNet-подобный query decoder — отдельное добавление после проверки общей иерархии. Query2box — последующая проверка составных запросов; он не является обязательным центральным bottleneck.

Название описывает нашу комбинацию проверяемых решений, а не новую опубликованную архитектуру. Нет основания утверждать, что HGT уже лучше текущего MLP/Graph на нашей музыке.

## 3. Представление: объекты сохраняются на всех уровнях

Предлагаемый state содержит:
- raw note и временные узлы, raw track identity;
- h — контекстные состояния наблюдаемых нот;
- H — отдельные кандидаты гармонических событий;
- P — отдельные кандидаты процессов;
- временные context/bar/block nodes для длинного контекста;
- типизированные рёбра, exact intervals, participant scope, устойчивые локальные IDs.

F/f первоначально остаются контекстными выходами над H/h; при необходимости отдельный assignment node связывает конкретное событие с конкретным тональным контекстом. Общий class prototype «доминанта» не заменяет экземпляры событий и не служит общим состоянием всех произведений.

P является узлом события/процесса с явными участниками. Это позволяет представить взаимодействие нескольких объектов без обязательного разворачивания в полный clique. Перекрытия допустимы; ноты не обязаны образовывать единственный softmax partition по H/P.

IDs адресуют объекты текущего произведения, а не становятся learnable corpus-ID embeddings. При повторных проходах отдельные H/P не теряют идентичность.

Наблюдаемые temporal/containment edges, геометрическое incidence и предсказанные semantic memberships различаются. Geometric inclusion не означает chord membership. Ноты с низким chord-member score остаются доступными: они могут быть ключевыми участниками разрешения.

## 4. Вычислительный цикл

Начальная ограниченная конфигурация для протокола: width128,4attentionheads,3повтора одного общего updater. Это инженерная отправная точка, а не найденные оптимальные гиперпараметры. Все сравниваемые варианты используют одну ширину и одинаковые head definitions.

Сначала raw/MIDI encoder создаёт пирамиду. Для note initialization доступны raw признаки и local/final C3 states; сравниваемые условия получают одинаковую информацию. Таким образом, decoder не обязан восстанавливать точный pitch/time из единственного агрегированного H.

Каждый повтор:
1. локальные note/context и временные узлы обмениваются типизированными сообщениями;
2. note/h→H: событие читает геометрически допустимые состояния участников;
3. H/h→P: процесс читает кандидатов событий и участников;
4. context nodes обмениваются информацией по всей поддержанной пьесе;
5. context→P→H→h/note: обратный проход уточняет нижние состояния;
6. node/edge heads уточняют свойства, objectness и semantic incidence scores.

Все states сохраняются. Используются residual connections, нормализация, gates и прямой доступ к начальным признакам. Общие веса повторов ограничивают число параметров, но вычислительная стоимость растёт с числом проходов.

Внимание зависит от source state, receiver state, типа связи, относительного exact-time-derived расстояния, scope и raw pitch/interval features там, где они определены. Кодирование времен использует точные исходные координаты; float features не используются для canonical matching.

Предсказанные incidence weights могут изменять дополнительный semantic channel. Базовый геометрический канал сохраняет доступ ко всем допустимым участникам, иначе ошибочное раннее membership отсечёт важные non-chord notes. Attention/gates являются обучаемыми весами, не доказанными вероятностями истинности или причинными объяснениями.

Схематичный будущий интерфейс:

```python
pyramid = encoder(observed_piece)       # live forward при дообучении
graph = build_raw_candidate_graph(observed_piece, policy)
states = initialize(graph, pyramid, raw_features)

for _ in range(3):
    states = updater.local(states, graph)
    states = updater.bottom_up(states, graph)
    states = updater.whole_piece(states, graph)
    states = updater.top_down(states, graph)
    hypotheses = heads(states, graph)
    graph = update_soft_channels(graph, hypotheses)  # без gold sidecar

return heads(states, graph)
```

Это псевдокод предложения, не существующий API. Hard candidate bank остаётся фиксированным на первом этапе; обновляются states и soft scores. Создание/удаление узлов между повторами — более сложная последующая абляция. Gold labels не передаются в forward или в динамические рёбра.

Однократный запуск C3 допустим: дальнейший updater повторно обновляет его выходные states, а при live forward gradients возвращаются в C3. Не нужно обязательно запускать весь C3 заново на каждом повторе. Кэшированные detached states не допускают градиент в C3; такой cache применим только в явно frozen контроле.

## 5. Построение H/P и данные

Семантическая иерархия не возникает просто из дополнительных GNN layers. Нужны кандидаты, различимые роли узлов и supervision.

Первая общая кандидатная политика использует raw temporal anchors и ограниченный список interval lengths; все условия получают один и тот же bank. Временные ограничения не подбираются по dev. Candidate recall и пропуски из-за scope/time limits обязательны.

H boundaries/attributes и P intervals/types доступны как потенциальные targets в существующей схеме; известные note-context fields и адресные relations добавляются отдельно. При неполной разметке unmatched candidate не становится negative. Участники P и directed roles должны проверяться по собственным полям/relations. Из D→T или одного нотного разрешения нельзя автоматически изготовить gold P.

Возможность обучать P detector зависит от числа независимых поддержанных works, нормализованного словаря и полноты процессов. Если этих targets недостаточно, upper span nodes остаются явно латентными контекстными объектами; их нельзя называть выученными разрешениями.

Все модели получают одинаковые маски и sampler. F/key/sonority/chord-degree/process values требуют согласованного TRAIN-only vocabulary; подробные авторские dicts нельзя превращать в тысячи случайных классов. Native и LLM-origin targets сохраняют provenance. Full graph analysis и human musical correctness остаются разными оценками.

Oracle H/P допустимы в отдельном diagnostic arm. Его результат не смешивается с raw-only end-to-end результатом. Предсказанные кандидаты, включая неверные, должны участвовать в основном train/inference режиме; точное сопоставление с targets выполняется снаружи forward.

## 6. Как охватить произведение и не потерять ноты

Локальные нотные рёбра обрабатываются по tiles с уникальным core ownership; halo обеспечивает контекст, а не дублирует целевые объекты. H/P, пересекающие tiles, имеют единый ID/геометрию и не удаляются только из-за границы окна. Часть реализации потребует нового assembler: старый H/member cache исключает H вне tile.

Для всей пьесы сохраняется последовательность context states, привязанных к bar/block времени. Global attention на этих узлах и обратный проход дают дальнему контексту путь к нотным предсказаниям. Подробные ноты остаются доступны локально и по явному обращению к участникам.

Существующие [WholePieceHCM encode_tiles/encode_from](../../src/music_critic/pll/whole_model.py) и [whole_memory](../../src/music_critic/pll/whole_memory.py) дают полезные seams и core ownership. Их генеративный decoder/PLL loss не требуется переносить в анализатор. Это повторное использование дизайна, не утверждение о готовом обученном whole-piece reasoner.

Сложность содержит стоимость sparse edges и операций по состояниям. Если global attention по M coarse nodes dense, остаётся член порядка M²; утверждать линейную сложность всей новой модели нельзя. Более короткие paths не гарантируют отсутствия нового coarse bottleneck. Нужны quality-by-length/distance, latency и память; online/causal режим отдельно от offline full-piece.

## 7. NBFNet и Query2box: конкретный интерфейс

Общий updater вычисляет состояния для всех задач. Затем optional query decoder получает:
`(graph, states, source_id, relation_type, candidate_ids)`.
NBF-like вариант добавляет source marker и relation-conditioned propagation, после чего оценивает всех допустимых адресатов данного запроса.

Это адаптация под музыкальный граф с наблюдаемыми признаками, а не буквальное применение pretrained KG-модели. Для разных sources/relations проходы могут повторяться; Q запросов создают отдельный cost multiplier. Поэтому первичные node/attribute tasks не должны требовать NBF запуска для каждого класса/пары.

Query2box branch получает те же candidate IDs и inductive states. Он строит представление запроса, но не обнаруживает H/P и не возвращает потерянные при pooling детали.

Для первого AND/path baseline предпочтительно сохранить явные scores/связи кандидатов и составлять ответы над ними. Для запросов с общим witness необходимо действительно соединять по одному H_id/P_id. Два независимых marginal scores «существует процесс» этого не гарантируют. GNN-QE даёт полезную set-based идею, но также не снимает ограничения выбранного query algebra. Boxes проверяются на таком же answer universe и совместной разметке, не на переименованных одиночных queries.

## 8. Минимальное сравнение

Первый научный вопрос: помогает ли повторный обмен между музыкальными уровнями, когда данные, кандидаты и доступный контекст одинаковы?

Начать с frozen одинаковых C3 features как контроля причины; это не конечная продуктовая архитектура.

| Условие | Механизм |
|---|---|
| A: feed-forward | Те же raw candidates и coarse context, однократная агрегация вверх, те же heads |
| B: repeated bottom-up | Те же типы узлов/головы, три повторения, без semantic top-down |
| C: repeated bidirectional | Та же модель/ширина/повторы, с H/P→нижние уровни |
| D: topology control | C с допустимой перестановкой incidence внутри type/time/scope buckets |

B↔C изолирует добавленный top-down канал лучше, чем сравнение только C с историческим64d MLP. Следует выровнять residual/self refinement depth; отключённые сообщения заменяются теми же self update вычислениями. Полное равенство FLOPs не предполагается: публикуются actual compute, активные параметры, число edges и latency.

В B/C local/global обработка и доступ состояний каждого уровня к общему coarse context одинаковы. Переключаются только обратные semantic incidence-сообщения от H/P к их нижележащим участникам. Это обязательная граница будущего config, чтобы удаление общего контекста не стало скрытой второй переменной.

D — дополнительная проверка конкретной структуры, а не доказательство музыкальной причинности. Перестановки должны сохранять допустимые типы/время/scope, иметь зафиксированный seed и обучаться в собственном режиме; если перестановка нарушает семантический контракт или невозможна, этот контроль не применяется. Одно test-time удаление рёбер измеряет ещё и distribution shift.

В первом bounded запуске можно ограничиться A/B/C; D — заранее запланированный отдельный контроль. Oracle geometry при необходимости имеет отдельный data regime. Основной raw bank и whole-piece assembly одинаковы по условиям.

После этого — маленькое сравнение лучшего контролируемого пути с baseline при одинаковом live дообучении C3. Для строгой проверки взаимодействия hierarchy×unfreezing допустим2×2план. Одинаковый freeze policy внутри сравнения не позволяет спутать эффект иерархии с адаптацией encoder. Scratch не нужен в первом этом опыте.

NBF decoder и boxes не перемножаются с начальным grid: добавляются отдельно после поддержки atomic tasks. Seeds/updates/selection/budgets фиксируются будущим протоколом до запуска; здесь они не утверждены.

## 9. Что измерять и что реализовать сначала

Предлагаемые первые task families:
- H boundary/object scores + sonority;
- h membership/degree;
- F/key на известных полях;
- P interval/type при достаточном support;
- p existence и выбор адресата с корректными negatives.

Помимо каждой task metric нужны: coverage, candidate recall, raw end-to-end typed-edge/answer quality, coherent shared-participant answers, known false positives и contradictory outputs. Оценка по works/families, длине пьесы и дальности зависимости проверяет заявленную ценность full context. Калибровка и пороги выбираются отдельно от exploratory dev. Weak-label agreement не превращается в human accuracy; TEST остаётся закрыт.

Первый implementation slice после specification:
1. graph/state contract с typed IDs, exact geometry, core ownership и target-sidecar separation;
2. общий raw candidate bank и matching/masks;
3. recurrent HGT-style updater с switches bottom-up/top-down/local/global;
4. одинаковые heads и shared trainer;
5. live C3 gradient path отдельным режимом;
6. optional query decoder позднее.

Обязательные synthetic checks: перестановочная согласованность с routing IDs; отсутствие влияния target sidecar на inputs; gradient из upper loss в нижние states и в live C3; отсутствие такого gradient в frozen режиме; смена результата при изменении релевантного соседства; masked unknown без negative gradient; held-note boundary и cross-tile ownership; сохранение перекрывающихся P; query shared-witness identity; padding/empty scopes; отдельный причинный режим при будущем online расширении. Эти tests подтверждают механику, не музыкальную пользу.

Для будущего протокола не хватает паспорта нормализованных H/P/F targets, полноты negative scopes, finite candidate policy и ресурсного gate на текущем сервере. Это конкретные зависимости перед запуском, не основания откладывать само проектирование.

## 10. Уточнение общей модели: прямой обмен h/H с P и гипотезы F/f

Уточнение обсуждения 27 октября 2026. Пользователь поддержал связь P с H и h,
включая доступ к их функциям/ролям. Ниже зафиксировано целевое предложение;
это не реализация, миграция текущей схемы или разрешение нового GPU запуска.

### Объекты и результат

| Объект | Содержание и идентичность |
|---|---|
| n | Наблюдаемая MIDI-нота; её атака и длительность уже известны |
| H | Кандидат гармонического события: интервал, scope, участники, свойства |
| h | Контекст ноты n относительно конкретного H и интервала их пересечения |
| F / f | Предсказываемые функция H / контекстные свойства и роли h |
| P | Кандидат процесса с интервалом, типом и конкретными участниками H/h |
| p | Направленная зависимость между конкретными контекстами/событиями, например resolves_to; в первой версии это типизированное ребро, не обязательный отдельный узел |

h не является новой физической нотой. У удержанной ноты могут меняться h/f
при смене H. Границы h выводятся из геометрии ноты и гипотез H; отдельный
неограниченный детектор нотных атак не требуется. F/f не обязательные этажи:
классы и вероятности принадлежат экземплярам объектов и выбранному контексту.
Общий класс функции не объединяет состояния разных появлений аккорда.

Основной scope — совместное звучание дорожек. Track identity сохраняется;
track не равен голосу. Локальные и групповые scopes допустимы, но начальный
список ограничивается raw политикой, а не всеми подмножествами дорожек.
Поддержка разметкой каждого scope проверяется отдельно. Перекрывающиеся
кандидаты допустимы; декодирование принятого аналитического view соблюдает
контракт эксклюзивности его гармонических состояний/контекстов. Альтернативные
views и перекрывающиеся P сохраняются раздельно.

### Forward и передача гипотез

1. Raw MIDI graph и C3 инициализируют множество note/time/context states.
2. Ограниченный raw bank предлагает H/P intervals; h создаются по допустимым
   пересечениям n и H. Gold границы, функции и полнота разметки не входят в forward.
3. Общий typed updater повторяет local updates, h↔H, H↔P и **h↔P**, а также
   одинаковый для сравниваемых условий доступ к coarse whole-piece context.
4. После каждого круга общие heads получают текущие H/h/P states и уточняют
   существование событий, свойства, участие и адресные p-связи.
5. Финальный decoder возвращает события, интервалы, вероятности свойств и
   типизированные связи с IDs; подробные состояния не заменяются одним song vector.

Прямой h↔P канал обязателен в предлагаемой полной модели: конкретная нота
может определять процесс даже при низкой вероятности chord membership.
Наблюдаемая геометрия и soft semantic participation — разные каналы.

Базовый вариант передаёт hidden states. Отдельная абляция добавляет к сообщению
проекцию **предсказанных** распределений F/f и свойств P предыдущего круга.
Так P видит гипотезы ролей, а нижние уровни — гипотезы процессов. На k+1
используются значения круга k; gold teacher forcing не нужен. Аннотационные
confidence/masks остаются в loss, не являются входными признаками.

Такой канал не гарантирует калибровку, объяснимость или согласованность:
возможна самоподдержка неверной гипотезы. Остаточные raw состояния сохраняются;
сравниваются ошибки/противоречия с вариантом hidden-only. C3 вычисляется один
раз за forward, но в live режиме получает градиенты от всей общей системы.

### Семейства обучающих задач

| Семейство | Выход / supervision | Проверка |
|---|---|---|
| Обнаружение H | Выбор raw начала/конца, objectness, совместимый scope | Candidate recall, boundary F1 с фиксированным допуском, segment overlap |
| Свойства H | Нормализованные созвучие, состав, root/quality/bass там, где известны | Masked per-field и joint качество |
| Контекст и F | Тональность, функция H относительно контекста | MacroF1 и покрытие независимых works |
| Участие h | Геометрический контекст отдельно от chord membership/degree | PR/F1/FPR на известных labels |
| Роль f | Разложенные note-role targets при наличии определения и поддержки | Per-role F1/coverage; degree не равен полному классу украшения |
| Обнаружение P | Интервал/тип процесса, участники и их роли | Event/participant/role качество; эти поля имеют отдельные masks |
| Адресные p-связи | Existence, тип, source и target | PR/F1 отдельно от Recall@1/5 и полного typed-edge качества |
| Совместный анализ | Согласованные адресные ответы по сохранённым IDs | Сквозные метрики с predicted H, противоречия, latency/memory |

Это семейства, а не восемь независимых encoders и не один огромный multiclass
словарь. Границы, бинарные свойства, многозначные роли и выбор адресатов требуют
разных heads/losses. Нормализация loss — по известным targets каждой задачи;
массы нотных targets не должны автоматически подавлять редкие процессы.
Число выходных полей определяется нормализованным словарём, не целью «20 задач».

Наличие полей в schema не устанавливает их достаточную поддержку в данных.
Существующие source/LLM targets дают основу H/properties, note-context и
адресных relation задач, но полнота P, редких f, направленных ролей и групповых
scopes требует отдельного паспорта. Если P supervision недостаточно, верхние
span states остаются латентными: их нельзя выдавать за распознанные разрешения.
Unmatched candidate не является negative без известной полноты данного scope.
Oracle H/P остаются отдельной диагностикой; основной результат требует raw
кандидатов и оценки без gold границ. Субъективное напряжение/эстетика не следуют
из имеющихся theory labels.

### Порядок проверки

Сначала сохранить ранее предложенное A/B/C сравнение hidden-state обмена.
В полной C присутствуют H↔P и h↔P. После проверки механики/поддержки отдельно
сравнить C с тем же C плюс soft F/f/P feedback; candidate bank, supervision,
C3 freeze policy и heads остаются общими. Live C3, NBF-like addressed decoder
и Query2box composition не перемножаются с этим в один первоначальный grid.
NBF/boxes используют построенный граф и проверяются после atomic задач.

Добавочные synthetic проверки для реализации: адресация h при held note и
смене H; независимость forward от gold F/f/P; лаг feedback на один круг;
перестановочная согласованность IDs; gradient и переключение direct h↔P;
сохранение raw доступа к non-chord notes. Это будущие tests; сейчас код не менялся.
Следующий шаг — task/candidate contract и спецификация первого bounded прототипа.
