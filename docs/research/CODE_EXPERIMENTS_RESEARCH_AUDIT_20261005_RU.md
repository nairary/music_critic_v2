# Music Critic V2: слабые места кода, экспериментов и направления исследований

5 октября 2026. Вопрос: что сейчас ограничивает качество критика, какую проверку
делать следующей и какие опубликованные методы можно практически использовать?

**Главный пробел — независимое подтверждение музыкального качества.** Проект уже
имеет содержательную инженерную основу, но улучшение предсказания скрытых нот,
распознавания гармонии и согласия с человеком пока не образует единой цепочки
доказательств. Ближайший полезный шаг — проверить целевую оценку и использование
контекста, прежде чем увеличивать модель.

## Слабые места кода и постановки

1. **Учебная цель пока не совпадает с конечной задачей.**
   [authored_data.py:285–296](../../src/music_critic/critic/authored_data.py)
   сохраняет `human_preference=unknown`, `label_kind=weak_author_intent`.
   HCM оптимизирует вероятность событий, включая EOS, а не предпочтение.
   Код честно различает эти величины; слабость в недостатке внешней проверки.
   Нужны правдоподобные хорошие, нейтральные и плохие альтернативы, новые
   произведения и независимые слушатели. Метаданные автора правки не входят
   в predictor.

2. **Нормировка по длине не решена для оценки качества.**
   [decoder.py:141–146](../../src/music_critic/pll/decoder.py) суммирует NLL;
   [scoring.py:47–51](../../src/music_critic/pll/scoring.py) делит его на события
   либо длительность, а для нуля событий NLL/event остаётся `None`.
   Сумма является корректной вероятностной величиной, но не автоматически
   сопоставимой эстетической оценкой. Простое запрещение пауз тоже неверно.
   Следует отдельно исследовать наличие материала/EOS, количество событий и
   содержание при фиксированной длине; калибровку выбирать на других работах.

3. **«Равно» пока нельзя обучать как известный исход.**
   [PairTargets, строки 83–87](../../src/music_critic/critic/targets.py)
   разрешает только ±1 для доступной метки; ноль означает отсутствие метки.
   Это допустимый нынешний бинарный контракт, но незавершённая часть Phase12.
   До использования человеческих оценок нужны separate tie/soft-preference
   semantics: «равно», «не уверен» и разногласие слушателей — разные состояния.
   [TRAIN percentiles](../../src/music_critic/critic/scoring.py) также не дают
   автоматически общей человеческой шкалы между произведениями.

4. **Наличие большой памяти не доказывает её полезность.**
   [motifs.py:331–348](../../src/music_critic/pll/motifs.py) умножает подробные
   извлечённые состояния на candidate weights; доминирование null может
   подавлять их вклад. Причина измеренного null dominance не установлена.
   Global уже поступает в local через
   [near_attention, whole_memory.py:278](../../src/music_critic/pll/whole_memory.py),
   в retrieval query и в relation families через
   [whole_model.py:126–144](../../src/music_critic/pll/whole_model.py).
   Отключение одного decoder attention не изолирует дальнюю информацию.
   Проверка должна менять удалённое содержимое во всех путях при неизменных
   локальном контексте, маске и цели. Inference ablation и обучение с выключенной
   веткой отвечают на разные вопросы.

5. **Устойчивость к представлению MIDI не установлена.**
   [whole_memory.py:80](../../src/music_critic/pll/whole_memory.py) содержит
   track embeddings, а [motifs.py:144](../../src/music_critic/pll/motifs.py) —
   признаки с индексом дорожки. Поэтому равенство оценки после перестановки
   дорожек не гарантировано. Это риск по структуре кода, не измеренная ошибка.
   Нужны проверки перестановки с согласованным remap запросов, переименования ID
   и MIDI roundtrip. Транспозиция/смена инструмента требуют собственной
   постановки: их музыкальная нейтральность не универсальна.

6. **Цена полного scoring скрыта за числом масок.**
   [score_piece:35–47](../../src/music_critic/pll/scoring.py) вызывает модель
   для каждого query; [whole_model.py:157](../../src/music_critic/pll/whole_model.py)
   каждый раз кодирует tiles всей пьесы. Текущий `encode_from` полезен при
   повторной работе с одним masked view, но сам не кэширует разные маски.
   Кроме того, block/song Transformer вычисляется даже при отключённом global
   выходе ([whole_memory.py:257–280](../../src/music_critic/pll/whole_memory.py)).
   Измерять следует полную стоимость 1/4/16 запросов, покрытие и peak memory.
   Затем можно оптимизировать отключённые ветки и кэшировать только доказанно
   неизменные masked tiles, проверяя эквивалентность и отсутствие утечки.

7. **Низкоприоритетный риск публичного trainer API после исключения.**
   [runtime.py:147–177](../../src/music_critic/pll/runtime.py) снимает `_in_step`
   в `finally`; после частичного сбоя optimizer вызывающий код может попытаться
   сохранить состояние при прежнем счётчике обновлений. Production
   [CLI:296–300](../../src/music_critic/pll/cli.py) так не делает.
   Повреждение исторических checkpoint не установлено; нужен synthetic fault
   injection и запрет дальнейшего save/step до восстановления после ошибки.
   В этом аудите это статически найденный риск, без runtime reproduction.

Положительная сторона: маскирование выполняется до графа, target и predictor
разделены, время и области запроса задаются точно, неподдержанные случаи
сохраняют coverage, реестр хранит отрицательные результаты. По просмотренному
коду оснований объявлять прямую утечку скрытых нот не найдено. Существующие
mutation-тесты полезны, но не являются доказательством музыкального качества.

## Что практически взять из литературы

При проверке [paperswithcode.com](https://paperswithcode.com/) перенаправляет
на [Hugging Face Papers](https://huggingface.co/papers/trending).

кода, а не заявление о полном просмотре актуального каталога Papers with Code.

HEAR особенно полезен постановкой прямой оценки, но отдельное добавление
hybrid loss в его Table2 снижает Track2 SRCC 0,897→0,892, одновременно улучшая
Top-Tier F1. Поэтому «добавить ListMLE» — гипотеза для ablation. Нынешние
same/unsure нельзя произвольно упорядочить для ListMLE. SongEval содержит аудио
и человеческие оценки; готовая парная MIDI-разметка не заявлена. Более чистая
общая проверка: наши MIDI → HCM, те же MIDI → фиксированный рендер → HEAR,
плюс независимые люди. Ошибки audio-to-MIDI здесь не нужны.

Наличие лицензии в корне кода не подтверждает автоматически одинаковые условия
весов, всех зависимостей и данных. До адаптации фиксируются версия и условия
конкретного компонента; в этом аудите ничего не скачивалось для исполнения.

## Порядок следующих проверок

1. **Зафиксировать целевую человеческую проверку.** Новые произведения,
   несколько слушателей, скрытая и рандомизированная A/B-подача,
   better/worse/same/unsure, отдельные аспекты и общий выбор. Все версии одной
   композиции и известные дубликаты — в одном split. Собирать независимые
   произведения важнее, чем много почти одинаковых правок. Удержать итоговый
   набор от выбора score/нормировки; публиковать coverage, согласие слушателей
   и неопределённость с группировкой по произведению.
2. **Проверить длину и контекст на существующих checkpoint.** Сначала
   inference-only: raw/per-event/EOS/count-сигналы; реальные паузы, вредные
   удаления и удачные разреженные варианты. Отдельно: полный/локальный/
   подменённый дальний контекст с выключением всех соответствующих путей.
   Важен выигрыш от правильного музыкального содержимого, не просто ненулевое
   значение attention. Не выбирать примеры по знаку модельного эффекта.
3. **Проверить небольшую quality-head.** Заимствовать постановку HEAR:
   замороженные представления, голова на человеческих данных, отдельно PLL
   и embeddings+PLL. Внешний MusicBERT/M2BERT — полезный контроль представлений.
   Это предложение отдельного исследования, не возврат отклонённых простых
   trained-control arms в прежнюю согласованную кампанию.
4. **Разобрать перенос C3 и дождаться terminal evidence C4.** Для POP смотреть
   per-class precision/recall, метаданные и common-support joint accuracy;
   не выбирать победителя по одному root-F1. C4 учит пять доступных heads;
   у остальных тринадцати нет POP supervision. Успех C4 не докажет качество HCM.
5. **Только при сигнале сравнивать память и SSL objectives.** Сохранить выбранный
   вопрос: свободная память против явных музыкальных понятий против понятий
   с остаточными признаками. Одинаковые masks, данные, decoder initialization,
   ёмкость/бюджет и несколько paired seeds. M2BERT objectives — отдельная ось,
   а не одновременная замена всего. Отрицательный результат тоже завершает
   гипотезу и позволяет не тратить ресурс на её масштабирование.

Критерий улучшения quality-модели — заранее определённый выигрыш на новых
человеческих сравнениях с оценкой неопределённости и сохранённым покрытием.
Критерий полезности памяти — отдельный воспроизводимый эффект правильного
дальнего содержимого. Результаты различать; ни один реальный прогон здесь
не запущен. Каждый будущий существенный запуск требует planned record и бюджета
по [EXPERIMENT_LOGGING](../EXPERIMENT_LOGGING.md).
